# Deploy & production operations (self-hosted Mac)

The concept docs cover subsystem behavior; this is the ops runbook for the live service.

## Auto-deploy flow

Which pipeline deploys a merge to `main` depends on the install: on a setup-installed copy the self-updater does it ([self_update.md](self_update.md)). The sections below document the mechanics a deploy relies on — the private-ref refresh, the restart classifier and the launch-configuration render — and the service they bring forward serves the FastAPI app + built UI at `http://127.0.0.1:8585`. Post-merge deploy *verification* (confirming a deploy actually landed) is separate from deploy *execution* and is answered by direct local observation rather than by inferring from a pipeline's own run conclusions — see `docs/architecture/deploy_verify.md`.

Service startup routinely takes 16–36s (engine-registry load + dispatcher start, longer on cold caches or right after a venv change), so a post-restart health check that polls `/api/health` needs a window of about 45s: a materially shorter window fails restarts that actually succeeded. A health-check failure after that window means the service took longer or is genuinely wedged: check `~/.alan/logs/alan.error.log`.

### Private-ref refresh (no shared ref contention)

The deploy checkout is a long-lived working copy shared with a process that cannot be paused for the deploy: alan's own running service fetches and writes refs in that same `.git` directory (`alan/worktree.py`'s `_resolve_base_ref`, `alan/base_ref.py`) whenever it resolves a base ref for a workspace, since both fall back to the service's own cwd when no `repo_root` is given. Before this refresh existed, the deploy's refresh step ran `git fetch origin main; git checkout -fB main origin/main; git reset --hard origin/main`, and `git fetch origin main` opportunistically updates `refs/remotes/origin/main` — a ref the live service's own fetches can also be mid-update on. A lock collision on that ref failed the fetch outright, red the whole deploy, and fired the "live build is stale" health finding — the exact condition the roadmap drivers refuse to dispatch under.

`alan/deploy_refresh.py::refresh(repo_dir, pushed_sha)` removes the contention by construction rather than by retry.

- **Obtains the target with no shared ref write.** `fetch_target` runs `git fetch --no-tags --no-write-fetch-head --refmap= origin +refs/heads/main:refs/deploy/target`, then resolves the tip by reading `refs/deploy/target` back with `git rev-parse`. `--no-write-fetch-head` matters because `$GIT_DIR/FETCH_HEAD` is itself a single per-repository file, not a ref, that a plain `git fetch` still appends to by default — the live service's own concurrent fetches append to that same file, and neither `fetch_target` nor `assert_ancestry` ever reads it back, so there is no reason to share writes into it even though (unlike the ref writes above) doing so has not been observed to fail the fetch outright on the git version this runs against. `refs/deploy/target` is a ref no other process in this working copy ever writes; `--no-tags` additionally suppresses tag auto-following, which would otherwise recreate the identical collision on the `refs/tags/deploy-*` tag each deploy mints. This privacy depends on deploy runs being serialised against each other — it must not be relaxed, or a second concurrent deploy run would itself contend for `refs/deploy/target`.
- **Targets the branch tip at refresh time, not the pushed commit.** The fetched ref is always `main`'s current tip; the pushed sha (the commit that triggered this run) is only the floor the tip is asserted against. This preserves the pre-existing convergence property: a later deploy run always moves the service onto the newest commit, so a run that fails after an earlier one succeeded cannot strand the service behind forever, and a rerun of a failed job after `main` has advanced still deploys the current tip.
- **Asserts ancestry before mutating anything.** `assert_ancestry` runs `git cat-file -e <pushed>^{commit}` to confirm the pushed commit is present at all, then `git merge-base --is-ancestor <pushed> <target>` to confirm the fetched tip actually contains it — in that order, because `--is-ancestor` itself exits non-zero on an unknown object, which would otherwise collapse "not present" and "not contained" into one indistinguishable failure. The check is reflexive (`tip == pushed` passes, since a commit contains itself), so an ordinary deploy where nothing raced always passes. Either failure — `PushedShaAbsentError` or `NotContainedError` — raises before `refresh` calls its mutation step, so a hard failure here leaves the working copy completely untouched: nothing is reset, checked out, or cleaned. This is strictly safer than a tolerant refresh that proceeds against a stale ref: doing so would deploy an older commit silently green, record the wrong `served_sha`, advance the restart marker's baseline to the wrong commit, and publish a deploy tag at the wrong commit — then read its own bad write back as healthy.
- **Refuses to run in a shallow repository.** `assert_not_shallow` checks `git rev-parse --is-shallow-repository` before anything else and raises `ShallowRepositoryError` rather than trust a grafted ancestry answer; the refresh itself never narrows history (no `--depth` on its own fetch), so a full checkout stays full.
- **Mutates only after every assertion passes**, in the same order the old inline step used: `git update-index --no-skip-worktree deploy/ai.alan.plist` (tolerating a clean index — see the skip-worktree paragraph below), `git checkout -fB main <target_sha>`, `git reset --hard <target_sha>`, `git clean -fdx` with the same three exclusions as before (`alan/web/node_modules`, `.venv`, `alan/web/dist*` — `alan.deploy_refresh.CLEAN_EXCLUDES`). No step in the mutation phase names `origin/main`; the reset target is always the 40-hex sha `assert_ancestry` just verified.
- **Writes `$DEPLOY_SHA`, not a re-derived `rev-parse HEAD`.** `scripts/deploy_refresh.py` publishes `DEPLOY_SHA=<target_sha>` to the caller's environment on success only, and every downstream step that needs the deployed commit reads `"$DEPLOY_SHA"` instead of computing its own `rev-parse HEAD`. The caller never shell-captures the script's stdout (no `DEPLOY_SHA=$(...)` substitution) — `set -e` swallows a captured command's non-zero exit inside `$(...)`, which would silently turn a hard failure green with an empty sha.

On any of the three failure classes, the CLI (`scripts/deploy_refresh.py`) prints a distinct message to stderr and exits 1 without publishing `DEPLOY_SHA`, so the refresh fails loudly and no later step sees a stale or empty `$DEPLOY_SHA`.

### Why the restart step kickstarts as well as bootstraps

`launchctl bootstrap` **registers** a service; it does not guarantee launchd spawns it. `~/Library/LaunchAgents` agents load into the `gui/<uid>` domain, and macOS puts that domain into **on-demand-only** mode whenever the Aqua session is backgrounded — in practice, whenever the console screen locks and the display sleeps. In that mode launchd honours demand-triggered launches but *queues* `RunAtLoad`, logging `pending spawn, domain in on-demand-only mode: ai.alan`, and holds the spawn until the session becomes active again. `KeepAlive` never rescues this, because the job never ran and therefore never exited. The restart step consequently ends with `launchctl kickstart -p "$LABEL"`, which per `launchctl(1)` runs the service "regardless of its configured launch conditions" — the flag is `-p` (print the resulting pid) rather than `-k` (kill first), so it forces the spawn when bootstrap deferred it and is a no-op when bootstrap already started the process. It is deliberately left unguarded by `|| true`: a spawn that cannot be forced should fail the step loudly under the leading `set -euo pipefail`, not be rediscovered 45s later as an opaque health-check timeout.

The failure this fixes is a **total-downtime** one, not a slow-start one, and it is trivially misread: a locked screen can leave the deploy's `bootstrap` returning 0 and printing its success line while the service does not actually start until the machine is unlocked, which is easily mistaken for a slow start or resource starvation. The one-command discriminator is `launchctl print gui/$(id -u)/ai.alan | grep -E "runs|last exit"`: `runs = 1` with `last exit code = (never exited)` proves the job was never spawned rather than crash-looping.

The old ordering also **falsely advanced the restart marker**, which is why the kickstart belongs before the marker write rather than anywhere else in the step. `~/.alan/deploy/restarted_sha` was written as soon as `launchctl bootstrap` returned 0, so for the whole outage the marker asserted that the live service had last been restarted at that commit while no process existed at all — precisely the claim the marker contract below promises it can never make. That is a correctness problem, not a cosmetic one: `bootstrap` has by then registered the job, so the restart decision's `launchctl print` probe reports it and sets `SERVICE_LOADED=true`, and the marker it diffs against already equals `HEAD`. A subsequent safe-path merge would therefore classify `safe_paths_only` and skip the very restart that would have revived the dead service, extending the outage instead of ending it. Putting `launchctl kickstart` ahead of the marker write restores the invariant that the marker is only reached once a process has actually been spawned. What is *not* wrong in this state is the deploy checkout itself, so an investigation should not go hunting for unmerged code — once the service finally spawns it runs the deploy's own commit.

### Conditional restart on safe-path deploys

Not every deploy needs to bounce the live service: a merge that only touches documentation, markdown anywhere in the repo, frontend sources, or tests changes nothing the running backend process has loaded, so restarting it just interrupts every in-flight worker for no benefit (measured over 713 historical deploy spans: ~34% of deploys, ~2.6 avoided restarts/day). `alan/deploy_restart.py` is the standalone, stdlib-only classifier module that makes this call (`is_safe_path`, `marker_reachable`, `changed_paths`, `decide`); `scripts/deploy_restart_decision.py` is a thin argparse + `$GITHUB_OUTPUT` wrapper around it, which the deploy's restart-decision step invokes as `python3 scripts/deploy_restart_decision.py`. The H8.4 restart-gate deferral (below) is the classifier's second caller, at merge time rather than deploy time — both callers import the same objects from `alan/deploy_restart.py` rather than each carrying their own copy, pinned by identity in `tests/test_scripts_deploy_restart_decision.py::test_script_reuses_alan_deploy_restart_objects`.

**Safe-set classification** — affirmative-match-only, no hot list:

| what | matches |
|---|---|
| `SAFE_DIR_PREFIXES` | `docs/`, `tests/`, `alan/web/` (segment-anchored prefixes) |
| `SAFE_SUFFIXES` | `.md` (any path, anywhere — including under `.github/`) |

A path is safe only if it matches one of those; every unmatched path is hot by construction, not by rule ordering — there is deliberately no companion "hot" list to keep in sync. `alan/` outside `alan/web/` (backend application code), `pyproject.toml` / `uv.lock` (dependency manifests), `deploy/` (deployment configuration), `scripts/` (repository scripts), and `.github/` (CI definitions) therefore all restart, with two carve-outs worth naming explicitly: `alan/webhooks.py` does **not** false-match the `alan/web/` prefix (it is a plain segment prefix check, not a substring check), and repository scripts stay in the restart bucket *even though `scripts/` is re-read per invocation* — this deliberately makes changes to the classifier itself restart-conservative, and the measured payoff from including `scripts/` in the safe set was too small to justify the subtler safety argument. CI definitions (`.github/`) are also deliberately **not** in the initial safe set: widening to them is a pre-planned follow-up after a week of clean skip decisions.

**Marker baseline.** The comparison baseline is not "the previous merge" but "the commit the running service was last actually restarted at": a marker file at `$HOME/.alan/deploy/restarted_sha` (outside the git checkout, so `alan/deploy_refresh.py`'s `git reset --hard` + `git clean -fdx` never touch it) records that commit sha. It is written **only** by the deploy's restart step, as its last two lines, positioned after `launchctl bootstrap` and the `launchctl kickstart` that follows it both return — the step opens with an explicit `set -euo pipefail` so a failed bootstrap *or* a spawn that could not be forced aborts the step before the marker is ever written, and the marker can never claim a restart that didn't happen. It is never written on a skipped-restart deploy. On a public copy, which has no deploy step, the marker is seeded by setup (`scripts/setup_macos.sh`'s `seed_deploy_marker`) and only after `wait_for_head` has seen `/api/health` report the service serving that exact `HEAD`. The self-updater's restart apply moves it from then on. Without the seed, every merge before the copy's first self-update restart classifies `missing_marker`: deploy_verify loses the 600 s ceiling deferral, and the updater fails closed to a restart even for a docs-only merge. The diff the classifier takes is baseline-to-new-`HEAD` (`git diff --no-renames -z --name-only <marker_sha> HEAD`), so consecutive skipped deploys accumulate into one union diff against the code the process is actually running — 18.6% of measured deploy spans cover 2+ merges, which is exactly why per-merge comparison would be wrong. `--no-renames` is load-bearing: with rename detection enabled, a file renamed out of a hot directory into a safe one (or vice versa) would show as a single `R` diff line and be classified only by its destination path; disabling it makes the diff report the old path as deleted and the new path as added, so a rename is always classified as a change to *both* paths.

A **missing marker** (fresh checkout, first deploy after this change ships) — `alan.deploy_restart.REASON_MISSING_MARKER`, the one reason string named as a constant rather than an inline literal, because `alan/teams/_deploy_restart_probe.py` (below) also returns it from its own pre-subprocess short-circuit — or a **marker sha unknown to the checkout** (`git cat-file -e <sha>^{commit}` fails — a shallow clone, a rewritten history, or a marker from a different repo/machine) both force a restart, same as a **service that is not currently loaded** (`launchctl print` fails — nothing to skip restarting *for*) and any **exception raised anywhere in classification** (`classifier_error`). An **empty union diff** (marker sha equals `HEAD` — e.g. a workflow re-run with no new commits) classifies as skip with reason `no_changes`: identical trees mean the running process is already executing exactly that code. Skipping is only ever the result of an affirmative match of *every* changed path against the safe set (`safe_paths_only`); anything else is `hot_paths`. This fail-closed rationale is the classifier's own contract, documented here rather than in a module docstring: `alan/deploy_restart.py` carries no docstring at all (per this repo's no-comments convention for `alan/`), and `scripts/deploy_restart_decision.py`'s docstring is trimmed to a pointer at this page rather than restating the rationale a second time.

Out-of-band restarts — a manual `launchctl kickstart`, a crash-and-relaunch, a machine reboot, or a restore of the runtime-state directory that rolls the marker file backward — all leave the marker stale-old relative to the process actually running. That only ever *widens* the next comparison (a larger union diff, more likely to contain a hot path) toward restarting, never away from it. This direction is intentional and must be preserved: the alternative (trusting a marker that might be ahead of reality) could produce a false skip.

**Fail-closed wiring.** The restart and the post-restart health check are gated on the decision output being anything other than the explicit string `'false'` — note the inversion. Gating on `== 'true'` instead would let an empty or unset decision output (the classifier's own defensive fallback, or a step that never ran) evaluate to `false` and silently *skip* the restart — fail-open on the single most safety-critical wiring detail. Restarting on anything except an explicit, affirmative `'false'` string is the fail-closed form; the warn-only liveness probe uses the mirror condition (an explicit `'false'`), so it only ever runs when a skip was explicitly decided.

**Frontend swap.** The previously built frontend must survive the checkout reset rather than being deleted by it — `git clean -fdx`'s exclude list now carries `-e 'alan/web/dist*'` alongside the existing `node_modules`/`.venv` excludes. `scripts/swap_web_dist.py` builds into one of two fixed slots (`dist.a` / `dist.b`, alternated by `next-slot`) and promotes the finished build into serving position with `os.rename` over a symlink named `dist` — never `mv` (BSD `mv` `stat()`s the destination through a symlink and would move the source *inside* `dist.a/` instead of replacing the link, and `mv -T` does not exist on macOS) and never a shell force-relink one-liner (same portability gap). `activate` takes a required `--sha` (the commit being built — `$DEPLOY_SHA`, the target sha `alan/deploy_refresh.py` verified) and writes it to `<slot>/.deploy_sha` **before** the `dist` symlink rename, so the file is never observable in a partially-active state; this is what `alan.deploy_observe.active_slot_sha` reads to answer "does the currently-serving frontend build contain this merge" for the deploy-verify restart-free arm (`docs/architecture/deploy_verify.md`). `activate` refuses to promote a slot without an `index.html` (a failed build) — and writes no `.deploy_sha` either in that case — and a first-run migration from a real `dist/` directory (pre-existing installs) renames the old directory aside, swaps the symlink in, then removes the old directory — there is never a window where `dist` is missing or partially written. Serialising deploy runs against each other is the invariant that prevents a second concurrent deploy from racing this swap. This closes a pre-existing defect present on every deploy before this change: a sustained window of hard 404s for the entire UI while `npm run build` overwrote `dist/` in place.

**Warn-only liveness probe.** On the skipped-restart path, service liveness is probed once (same URL, same curl flags as the restart-path health check). A failing probe logs `::warning::Alan liveness probe failed on the skipped-restart path; the service was already unhealthy before this deploy` — wording deliberately sharing no phrase with the restart path's `Alan: failed health check after 45s`, so the two are distinguishable in logs — and the step unconditionally `exit 0`s. It never fails the deploy: a service already wedged before the merge must not turn a documentation change into a failed deploy.

**Diagnosing a misclassification.** The restart-decision step prints its reason and every changed path with its safe/hot verdict to stdout, so a wrong skip-or-restart call is diagnosable from the deploy's log alone, without re-deriving the diff by hand.

### Served-sha health field

`GET /api/health` now includes `served_sha`, the git commit sha the running process was started from (`alan/served_sha.py`, `@functools.cache`d, warmed once in `lifespan` before `yield` — the cache is what makes the field mean "sha at process start" rather than "sha now"; it self-locates via `Path(__file__).resolve().parent.parent` and never imports from `alan`, keeping it an unambiguous bottom import layer). This is the observable that makes a wrongly-skipped restart detectable at all: before this field existed, a stale process answered health probes indistinguishably from a fresh one, so post-merge `deploy_verify` passed trivially whether or not a restart actually happened. `served_sha` is `None` if `git rev-parse HEAD` fails, times out, or the `git` binary is unavailable. This change adds only the field, its tests, and this documentation — no existing consumer of `/api/health` changes behaviour, and no automated alerting on a `served_sha` vs. deployed-sha divergence exists yet (see follow-ups below).

### Restart-gate deferral shortening (H8.4 / H8.5)

`alan.teams.deploy_verify.restart_gate_terms` (mechanics: `docs/architecture/deploy_verify.md`) asks `alan/teams/_deploy_restart_probe.py::classify_merge` for the same restart/skip verdict this page documents, at merge time — before the deploy pipeline itself has even started, let alone reached its own restart decision. That verdict decides whether `deploy_verify`'s enqueue pays the `_RESTART_WINDOW_S` deferral (now **600s / 10 min**, down from the original unmeasured 1200s/20min default) or starts immediately.

`classify_merge` returns a 3-tuple, `tuple[bool, str, str | None]` — `(restart_free, reason, merge_sha)`. The third element (added for H8.5, the signal-driven start) is the same merge-commit SHA `_merge_commit_sha` already resolves internally before fetching it; no new subprocess call. It is `None` whenever the SHA itself was never resolved (`missing_marker`, `merge_sha_unavailable`) and populated whenever it was, even on an otherwise restart-required verdict (`fetch_unavailable`, `service_not_loaded`, `hot_paths`) — `alan.teams.deploy_verify._restart_free_terms` uses it to ask `alan.deploy_signal.merge_is_served(merge_sha)` whether the live process already runs code containing this merge before falling back to the deferred ceiling.

**One classifier, two call sites, tied by identity.** `alan/deploy_restart.py` is the sole implementation; `scripts/deploy_restart_decision.py` (the deploy's restart decision) and `alan/teams/_deploy_restart_probe.py` (the merge-time deferral above) both import its four names verbatim rather than reimplementing any part of them. `tests/test_scripts_deploy_restart_decision.py::test_script_reuses_alan_deploy_restart_objects` pins this by identity (`is`, not behavioral equivalence), so the two call sites cannot silently diverge — the brief's central design tension, resolved structurally rather than by convention.

**Ordering problem: merge-time vs. deploy-time.** The deferral decision is made the moment a PR merges; the deploy pipeline's own restart decision runs later, against `origin/main`'s tip once CI checks out. `classify_merge` closes that gap by classifying against the *merge commit's own diff*, not against whatever local `HEAD` happens to be: it resolves the PR's `mergeCommit.oid` via `gh pr view --json mergeCommit`, fetches that single object id with `git fetch --no-tags --quiet origin <sha>` — no refspec, so the fetch writes only the object and `FETCH_HEAD`, updating no ref under `refs/` — and passes it to `alan.deploy_restart.decide(..., rev=<sha>)`, which the classifier now accepts instead of always diffing to local `HEAD`. This is deliberately not a refspec-based fetch or a `git pull`: the live deploy checkout runs `checkout -fB`/`reset --hard` around the same time on the same clone, and any ref-write from the probe's fetch would contend for the same ref/index locks. An object-id fetch cannot contend, because it never touches a ref.

**Marker path.** The probe reads the same on-disk marker CI writes, via `roots.deploy_marker_root() / "restarted_sha"` (`alan/roots.py`) — `state_root().parent / "deploy"`, which resolves to the same `~/.alan/deploy/restarted_sha` literal the deploy passes via `--marker`. No new `ALAN_*` environment variable was added: the derived path inherits `ALAN_STATE_ROOT` isolation everywhere that variable is already threaded (tests, e2e), the same way `cache_root()` already does.

**Transport.** The fetch routes through `secrets_store.transport_env()`, the same single choke point every other network git call in this repo uses (see "Transport injection" below); `alan/teams/_deploy_restart_probe.py` is canaried alongside the other three call sites in `tests/test_transport_canary.py`.

**Fail-closed, unconditionally.** Every input the probe cannot obtain — no on-disk marker, no resolvable merge SHA, a fetch failure (including a missing transport credential), a `launchctl print` failure or timeout, or any unexpected exception — routes to the ordinary deferred `ceiling` branch, exactly as before this change; only an affirmative `safe_paths_only`/`no_changes` verdict from `decide()` skips the wait via the `restart_free` path. This mirrors the restart classifier's own fail-closed table above: being needlessly slow is always acceptable here, being torn down mid-verify is not. **No signal ⇒ ceiling** is the same posture applied one level up, at the signal-driven start (H8.5, `docs/architecture/deploy_verify.md`): whenever `merge_sha` did resolve but `alan.deploy_signal.merge_is_served(merge_sha)` returns `False` — the live process genuinely hasn't caught up yet, or `served_sha()` itself is unavailable, or the `git merge-base --is-ancestor` subprocess fails or times out — `deploy_signal.merge_is_served` fails closed to `False` with no exception path, and the gate falls through to the deferred `ceiling` branch exactly as if no `merge_sha` had resolved at all. Proceeding as if verification were ready is never the fallback for an unreadable or untrusted signal; the ceiling always is.

**Accepted residual.** A merge that lands *between* `classify_merge`'s classification and the deploy pipeline's own checkout can still theoretically race a prompt-started `deploy_verify`, if that later merge is itself a hot-path change — the classification is a point-in-time read, not a lock held across the deploy. This is bounded, not eliminated: `DeployVerifyTeam.restart_rederivable = True` (`alan/teams/deploy_verify.py:155`) means a restart that does happen re-derives the job from scratch afterward rather than losing it, the same safety net that already covers a slower-than-window deploy today (`docs/architecture/deploy_verify.md`). Alerting on `served_sha` vs. deployed-sha divergence, which would close this residual more tightly, is separately tracked (see follow-ups below) and out of scope here.

### Stale live process alerting — delivered

`alan/live_staleness.py::detect()` is the automatic detector for the residual named in "Served-sha health field" above: it compares `served_sha()` (base — the commit the running process was actually started from, not the restart marker) against the `main_ci` triage surface's `obs["sha"]` (target — the tip of every push to `main`, since `tests.yml` has no path filter, so it stays current even when the deploy workflow itself never ran). It reuses `alan.deploy_restart.classify_range` (the same function `decide()` now delegates to) for the "did anything the running backend actually loads change" judgement — zero new safe-path rules, zero reimplementation. `alan/teams/triage.py::_stale_live_process_surface` wires it into the triage sweep as a `ClassifiedSurface` (`kind="stale_live_process"`, `surface_id=f"stale_live_process:{target_sha[:12]}"`) built from surfaces the sweep already gathered — no new network call. `alan/health.py` renders it `critical` + `deep_link`, same class as `worker_pool`.

**Why the target is `main_ci`'s sha, not the restart marker or the deploy run's sha.** The restart marker (`~/.alan/deploy/restarted_sha`) only moves on a deploy-driven restart — a kickstart, crash-restart, or reboot leaves it stale in a way that would read as a false alarm here, the opposite of `decide()`'s fail-toward-restart bias. The `deploy` surface's own sha can still lag behind `main_ci`'s: the deploy pipeline now triggers on every push to `main` unconditionally rather than only after a successful `Tests` run, so a red main no longer freezes the deploy surface the way it once did — but a deploy run can still fail its own dependency sync, frontend build, or health check, or simply not have completed yet, and either case leaves the deploy surface's sha behind `main_ci`'s advancing tip. This detector catches that residual lag regardless of cause. `deploy`'s surface is still consulted, but only for its `status` (in-flight gating below), never its sha.

**Inverted failure direction.** `decide()` fails toward restarting because a needless restart is cheap; this detector fails toward silence because a false alarm is the one failure mode that destroys an alert's value. Every gate below returns a named silence reason instead of a finding when its input is missing, unreadable, or ambiguous, and `detect()`'s outer `except Exception` catches anything unanticipated the same way. `_cheap_silence_reason` runs the pure, no-subprocess checks first; `_git_silence_reason` runs the local-git checks only once those pass:

| reason | gate |
|---|---|
| `no_served_sha` | `served_sha()` is `None` (`git rev-parse HEAD` failed at process start) |
| `target_not_sha` | the `main_ci` surface has no 40-hex sha (unreadable `gh` response) |
| `no_divergence` | served equals target — the common case, ~two-thirds of deploys |
| `main_ci_incomplete` | the latest push's CI run hasn't finished (`status != "completed"`) — a merge that landed moments ago |
| `deploy_unknown` | the `deploy` surface's obs is empty (`_unknown_deploy` — the `gh` read itself failed) |
| `deploy_in_flight` | the `deploy` surface's `status != "completed"` — a deploy is actively running |
| `not_ancestor` | served is not an ancestor of target (`git merge-base --is-ancestor`) — an unexpected divergent state |
| `target_unreachable` | target's sha is not resolvable in the local checkout (reuses `deploy_restart.marker_reachable`) |
| `within_settle_window` | target's committer timestamp is newer than `SETTLE_WINDOW_S` (1200s) ago — a deploy may still be mid-flight |
| `safe_paths_only` / `no_changes` | `classify_range` found only safe-path (or zero) changes — a legitimate skipped restart |
| `error` | any other exception anywhere in `detect()` |

Only when none of these fire — and `classify_range` returns `hot_paths` — does `detect()` return a `StaleLiveProcess(served_sha, target_sha, hot_paths)` and the sweep raise a finding. `alan/teams/triage.py` logs the silence reason (at INFO) whenever it isn't `no_divergence`, so a wrong silent call is diagnosable without re-deriving it by hand; `no_divergence` alone is skipped to avoid logging on essentially every sweep.

**Accepted residuals.** `target_unreachable` is possible whenever the deploy host's checkout is behind `main`'s actual tip (no `git fetch` is added here — this detector performs no network calls beyond what the hosting sweep already makes) — it degrades to silence rather than a false alarm, and a red main is already surfaced by the existing `main_ci` finding, so the frozen-deploy case isn't left blind even when this residual is hit. `SETTLE_WINDOW_S` (1200.0) duplicates `alan.teams.deploy_verify._RESTART_WINDOW_S` (also 1200.0) rather than importing it: `deploy_verify` sits below `live_staleness` in the import-layers list (`live_staleness` is placed between `roots` and `served_sha`, deliberately earlier than everything it needs to import), so unifying them would require moving one of the two, which isn't otherwise motivated by this change.

**Never remediates.** `detect()` and `_stale_live_process_surface` only classify and report; nothing here restarts the service, re-runs a deploy, or dispatches remediation work. The finding participates in the ordinary triage dismiss/re-surface machinery (`triage_pregate.decide()`'s per-`surface_id` fingerprint tracking) for free, since that machinery is already kind-agnostic — a finding stops recurring once `served_sha()` catches up (the surface simply stops being produced) and a *new* divergence re-surfaces under a fresh `surface_id` (the target sha changes). Making post-merge verification consult this signal is explicitly deferred, to accumulate real-world data on how often genuine divergence occurs before anything blocks on it.

## Launch configuration: template + render

`deploy/ai.alan.plist` is a **tracked template**, not the file launchd loads. It carries three placeholder tokens. `__ALAN_REPO_DIR__` and `__ALAN_HOME__` stand in for every machine-specific path (the launcher path, `WorkingDirectory`, `PATH`, `VIRTUAL_ENV`, `ALAN_SLOT_POOL_ROOT`, and the two `Standard{Out,Error}Path` entries). `__ALAN_SLOT_REPO_URL__` fills the `ALAN_SLOT_REPO_ROOT` value, the default engine's slot-pool clone source (see `docs/architecture/slot_pool.md`); the key's name and meaning are unchanged. launchd's plist format performs no variable expansion inside `EnvironmentVariables` or any other key, and launchd resolves `ProgramArguments[0]` before applying `WorkingDirectory` — so a machine path cannot be relativized inside the file itself; it must be substituted *before* launchd ever reads it.

`deploy/render_plist.sh` is the idempotent render step that does the substitution. It takes **no arguments** and derives everything from the environment: the repo directory from its own script location (`$(dirname "${BASH_SOURCE[0]}")/..`) and the target from `$HOME`. It refuses to run — exit non-zero, no write — when `HOME` is unset, so an unsandboxed render is structurally impossible rather than conventionally avoided. It writes the substituted content to a temp file created with `mktemp` **inside** the target's own directory (`~/Library/LaunchAgents/`, created idempotently with `mkdir -p` if missing — it does not exist on a fresh machine) and `mv -f`s that temp file over whatever currently sits at `~/Library/LaunchAgents/ai.alan.plist`, file or symlink. It never writes through the target path: if that path is a symlink pointing back into this tracked template, writing through it would dereference into the live checkout and corrupt the tracked template with a rendered, machine-specific copy. `mv` on the same filesystem is atomic, so there is never a window where the target is a partially-written file. Rendering twice produces byte-identical output.

**Where `__ALAN_SLOT_REPO_URL__` comes from.** The render reads the `origin` remote of the checkout the script belongs to — `git -C "$REPO_DIR" remote get-url origin` with `GIT_DIR` and `GIT_WORK_TREE` unset — never the caller's working directory, so a render launched from an unrelated repository, or with a stray `GIT_DIR` in its environment, still reads its own checkout. Three origin forms are accepted, each with or without a trailing `.git`: `https://github.com/<owner>/<repo>`, SCP-style SSH (`git@github.com:<owner>/<repo>`), and `ssh://git@github.com/<owner>/<repo>`. Every accepted form is normalized to `https://github.com/<owner>/<repo>.git`. Any user-info in the origin (a username, a token, a `user:password` pair) is discarded before anything is derived from it, so a credential embedded in the remote URL never reaches the rendered file, stdout or stderr.

**The origin grammar is exact and has one definition.** The host is the lowercase string `github.com` and nothing else: an uppercase or mixed-case host (`GitHub.com`), an explicit port (`github.com:443`), a trailing `/` (also after `.git`), a query string, a fragment, a percent escape and any leading or trailing whitespace are all unusable, as are `http://`, `git://`, a local path and any other host. The path is exactly one owner and one repository. An `<owner>` is 1 to 39 characters from letters, digits and `-` and does not start with `-`. A `<repo>` is 1 to 100 characters from letters, digits, `.`, `_` and `-`, measured after one trailing `.git` is stripped (so `r.git.git` is the repository `r.git`, a bare `.git` is empty and refused), and is never `.` or `..`. The character classes are spelled out explicitly in the script, not as ranges, so locale collation cannot widen them; the validated set also makes the value injection-safe for the `sed` substitution, which cannot see `#`, `&` or `\` in it. The same grammar exists in three places that must agree: the `ALNUM_CHARS`, `NAME_CHARS`, `OWNER_RE`, `REPO_RE`, `HTTPS_ORIGIN_RE`, `SSH_ORIGIN_RE` and `SCP_ORIGIN_RE` lines and the `parse_origin` function, which are byte-identical in `deploy/render_plist.sh` and `scripts/setup_macos.sh`, and `alan/self_update/_origin.py`, the Python restatement the self-updater uses ([self_update.md](self_update.md), "What counts as a GitHub origin"). `tests/test_deploy_render_origin_parity.py` compares the shell lines and function text between the two scripts and pushes one table of origins (uppercase host, explicit port, trailing slash, look-alike hosts, bounded and over-long names, `.`-only repositories) through the renderer, setup's `parse_origin` and the self-updater, requiring the same accept-or-refuse answer and the same slot URL from all three. Widening the grammar in one place without the others fails that test.

**Refusal, with no fallback.** When the tree is not a git checkout, has no `origin`, or the origin does not satisfy the grammar above, the render exits `78` (`ORIGIN_REFUSED_EXIT`, the sysexits `EX_CONFIG`) with exactly one line on stderr: the origin is not a GitHub repository, so worker slots have no repository to clone from; nothing was written; and the fix, `git -C "<checkout>" remote set-url origin https://github.com/<owner>/<repo>.git`. The refusal happens before `mkdir -p`, `mktemp` or any write, so an existing launch configuration — a regular file or a symlink — is left byte-identical, an absent one stays absent, `~/Library/LaunchAgents/` is not created, and no temporary file is left behind. The message never echoes the origin value, which may carry a credential. There is no default clone source anywhere under `deploy/`: shipped code never substitutes a repository the install did not name, and a test pins that the renderer's source holds no fallback constant. A usable origin renders exactly as it did before. Each caller reacts to the refusal in its own way: setup treats any non-zero render as a failed render and restores the previous file ([setup.md](setup.md), "Start sequence"); the self-updater checks the origin with the same grammar before it changes anything and records `blocked` / `no_github_origin`, and its rollback treats exit `78` as "the launch configuration was kept" ([self_update.md](self_update.md), "The render and the origin"); the deploy workflow runs `bash deploy/render_plist.sh` unchanged, so a deploy checkout whose origin became unusable now fails at the render step, before teardown, instead of installing a launch configuration that clones worker slots from another repository.

**Path rejection.** If the repository directory or `$HOME` contains `#`, `&` or `\`, the render exits non-zero with a fixed message that names only which directory it was (`repository directory` or `home directory`). The check runs before `mkdir -p`, `mktemp` or any write, so an existing target is left byte-for-byte unchanged, an absent target stays absent, and no temporary file is left behind. These are the characters that would corrupt the `sed` replacement text (`#` is its delimiter, `&` expands to the match, `\` escapes); an unusable origin is a different refusal (exit `78`, above), so the two are told apart by exit status: `1` for an unset `HOME` or an unsafe path, `78` for an origin. The path checks run first.

**`PATH` entry.** The rendered `PATH` carries `/opt/homebrew/opt/node@22/bin` directly before `/opt/homebrew/bin`, so setup never has to force-link Homebrew's `node@22` over the user's own Node.

The render needs only `bash`, `sed` and `git` — no project virtualenv and no application module, because it runs before `uv sync` — and targets macOS's stock `/bin/bash` 3.2 (no `${x,,}`, no associative arrays).

**The render runs before teardown.** The render step runs before the service is torn down, not merely before it comes back up. A broken render then aborts the deploy while the old process is still live and serving traffic; rendering after teardown would instead leave the service down with the very step that would fix it (the render) also broken, with no live process anyone deploys a fix against.

`deploy/run_alan.sh`'s interpreter is now derived from the script's own location (`"$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)/.venv/bin/python"`), not a hardcoded absolute path. If `deploy/ai.alan.plist` is edited without a subsequent deploy, the rendered file at `~/Library/LaunchAgents/ai.alan.plist` stays stale until the next deploy re-renders it — editing the template has no live effect on its own.

## Bind host/port override chain

`alan/bind.py`'s `resolve_host()` / `resolve_port()` replace the launcher's hardcoded `--port 8585 --host 127.0.0.1` flags: `deploy/run_alan.sh` now execs `python -m alan` with no bind flags at all, and `alan/__main__.py` resolves the effective host/port itself. Precedence, highest first: an explicit `--host`/`--port` CLI flag, then `ALAN_HOST`/`ALAN_PORT` from the environment, then the literal default (`127.0.0.1` / `8585` — unchanged from before this change). An empty or whitespace-only env value is treated as unset. `ALAN_PORT` set to a non-numeric value or a value outside `[1, 65535]` falls back to the default rather than refusing to boot — the same garbage-falls-back-to-default convention `float_env` already uses for tuning knobs like `ALAN_COMPLETENESS_THRESHOLD` (see "Tuning knobs" below). Both names are classified `ops tuning knob` in `tests/env_var_classification.py`: `alan/bind.py` is the sole reader of both (`alan/__main__.py` only calls it), which is what makes their registration legitimate rather than stale-entry bait — `tests/test_env_var_classification.py::_discover_env_vars` only scans `alan/**/*.py`, so a shell-only env name could never be registered there in the first place.

**Bind guard.** After the host is resolved, `alan.bind.bind_refusal()` judges the effective host (the value that wins the precedence above, with its source: `--host`, `ALAN_HOST` or the default) and `alan/__main__.py` calls it straight after argument parsing. The accepted set is any IPv4 literal in `127.0.0.0/8`, `::1`, and the exact lowercase name `localhost`; every other value is refused, whatever the environment contains, including `0.0.0.0`, `::`, LAN and public addresses, `127.1`, a scoped or bracketed `::1`, an IPv4-mapped loopback, `LOCALHOST`, `localhost.`, and any other hostname. No DNS lookup is made, so a custom alias that a hosts file maps to loopback is refused too. Nothing in the environment lifts the check: the container recipe (`docs/roadmap/docker.md`) adds its own non-loopback opt-in together with the container-mode authentication item (D7), not before. On refusal `__main__` exits 1 through `SystemExit(<message>)` before `_configure_logging()` and before uvicorn imports `alan.server`, so the application never loads. The one-line message names the rejected value and its source (`--host` or `ALAN_HOST`). With no host flag and no `ALAN_HOST` the default `127.0.0.1` is accepted and the service starts exactly as before; precedence is unchanged, and the guard only judges the result. The refusal exists because the Host-header allowlist is not authentication: a non-browser client can send any `Host` header, and the routes that need no control token create and dispatch work (see `docs/tutorials/security.md`).

**Operational note.** Services started from the shipped launch configuration set neither `ALAN_HOST` nor a host flag, so they bind loopback and keep starting through the restart this guard's deploy triggers. A refused host is a fail-fast: under launchd `KeepAlive` the service restarts, refuses again and crash-loops, with the refusal message in `~/.alan/logs/alan.error.log`. Recovery: remove the `ALAN_HOST` line from `~/.alan/secrets.env` (or correct it to a loopback value) and kickstart (`launchctl kickstart -k gui/$(id -u)/ai.alan`).

## Launcher + secrets contract

The launchd job runs via the `deploy/run_alan.sh` launcher, not `python -m alan` directly: `ProgramArguments` is `/bin/bash` with the rendered absolute path to the launcher (absolute because launchd resolves the program before applying `WorkingDirectory` — the render step above is what produces that absolute path from the tracked template), which loads machine-local secrets from `~/.alan/secrets.env` (plain `KEY=value` lines, read literally — not shell-evaluated; override path with `ALAN_SECRETS_FILE`) and then `exec`s `python -m alan` with no bind flags — host/port resolve via the override chain above, landing on the unchanged effective defaults `127.0.0.1:8585` with nothing configured.

Secrets MUST live in that file, never in the git-tracked `deploy/ai.alan.plist`: the deploy's `alan/deploy_refresh.py` does `git reset --hard` onto the verified target sha (never `origin/main` — see "Private-ref refresh" above) + `git clean -fdx` on the deploy checkout, so any in-plist edit is reverted on the next deploy — and an in-plist + `git update-index --skip-worktree` workaround wedges *every* deploy once a commit changes the plist (`error: Entry 'deploy/ai.alan.plist' not uptodate. Cannot merge.` → exit 128). `~/.alan/secrets.env` lives outside the checkout and is untouched by reset/clean; `chmod 600`. As defence in depth, `alan/deploy_refresh.py`'s mutation phase runs `git update-index --no-skip-worktree deploy/ai.alan.plist` after the ancestry assertion and before any tree movement, so a stray skip-worktree bit can never re-wedge a deploy.

## Verifier bot token bootstrap (`ALAN_VERIFIER_GH_TOKEN`)

Default empty; read from `~/.alan/secrets.env` via the launcher. When set to a non-empty PAT, the verification team's `gh pr review` and `gh api .../pulls/N/reviews` calls run with `GH_TOKEN=<that>`, authenticating as a dedicated bot account so GitHub does not reject the review as a self-review (mechanism + scope details: `pr_iteration_pipeline.md` §D15). A setup-installed copy configures it through the `verifier` step ([setup.md](setup.md), "The verifier bot").

alan reads the engine's `reviewer` record in the secrets store below (`POST /api/secrets` with `purpose: reviewer` and an optional `expires_at` as `YYYY-MM-DD`) first; `ALAN_VERIFIER_GH_TOKEN` in `~/.alan/secrets.env` is the fallback, read only when no `reviewer` record exists. An install whose profile declares `requirements` counts only the stored record, because readiness reads only the store (`engine_preflight.md`, "Dispatch readiness").

Scope: review POSTING, review DISMISSAL, and — after an approving pass whose raw CRITICAL count is 0 and was actually reported — READING and RESOLVING the verifier's own reply-free review threads (`_verifier_thread_resolution`), gated on `gh api user` confirming this credential's login equals the configured verifier login (`verifier_identity()`, below); a repository with no reviewer credential resolves nothing and never falls back to a default login, and an install with no verifier login configured resolves nothing at all, whatever credential it holds — on an install with no installed default-engine profile, implementation_fix's thread reading, `gh pr create`, `gh pr merge`, and `scripts/alan_copilot_resolve.py` keep the default `gh auth` identity. The per-call identity is conditional on the install being a copy: on a copy (an install with an installed default-engine profile) every forge call alan makes from the host carries the target repository's transport credential, or the reviewer credential, falling back to the transport credential, where the call acts as the reviewer, and is refused with `gh` never invoked when no credential resolves; `scripts/alan_copilot_resolve.py` runs outside that path and keeps the default `gh auth` identity. A stray `engines/default_profile.yaml` under the state root of an install without one switches it to copy identity at the next restart, and profile resolution only logs a warning when both files exist. On an install with no installed default-engine profile, if `GH_TOKEN` is already set in the service environment, `gh` uses it for those non-review calls too; `ALAN_VERIFIER_GH_TOKEN` does not strip or override `GH_TOKEN` for any subprocess other than the review-posting/dismissal and verifier-thread read/resolve calls. The bot login is `_pr_branch.verifier_identity()`, resolved in this order: `ALAN_VERIFIER_LOGIN` from the service environment (stripped; a blank value counts as unset), then the default profile's `verifier_login` field ([engine_config.md](engine_config.md), "Profile schema"), then nothing. There is no built-in login. With nothing configured, "not configured" is a distinct state (`None`), never an empty login: no review counts as the verifier's verdict, no review is dismissed as a stale verifier review, no thread is resolved as the verifier's, and no account is exempted from the stranger-thread filter on the verifier's behalf — including a review or thread whose author is missing or empty. [setup.md](setup.md) ("The verifier bot") records the login a setup-installed copy uses, and [pr_iteration_pipeline.md](pr_iteration_pipeline.md) (D28) and [forge_port.md](forge_port.md) list every consumer.

## API-managed secrets store (multi-repo credentials)

`~/.alan/secrets.env` (above) is the machine-local launcher bootstrap file — it stays the source for `SONAR_TOKEN` and the fallback for the default engine's `ALAN_VERIFIER_GH_TOKEN`, which is read only when no `reviewer` record exists. Alongside it, `alan/secrets_store.py` is a second, API-managed store for per-**engine × purpose** credentials (alan reads two purposes, `transport` and `reviewer`) for engines beyond the default. It is a directory of one `0600` JSON file per key under `ALAN_SECRETS_STORE_ROOT` (default `~/.alan/secrets`), each written atomically (temp file + `os.replace`). `POST /api/secrets` and `DELETE /api/secrets` write and remove a `{engine, purpose, value}` record; `GET /api/secrets` and every other surface (logs, audit JSONL, SSE) expose only `name` (`engine:purpose`) plus a `fingerprint` — a truncated (~12 hex) SHA-256 of the value, never a token prefix — plus `last_verified`; the raw value is write-only and never round-trips back out of the API.

`secrets_store.resolve_secret(engine, purpose, env_fallback=credential_env_name)` resolves **store-first, env-fallback**: if no record exists for the key, it falls back to reading `env_fallback` from `os.environ`, exactly the semantics `ForgeConfig.credential_env_name` / `CodeQualityConfig.token_env_var` already had. The fallback *is* the migration path — no separate tooling moves a credential out of `secrets.env`; it keeps working there until someone `POST`s the same value into the store, at which point the store takes precedence. The default engine's `ALAN_VERIFIER_GH_TOKEN` and `SONAR_TOKEN` therefore keep working completely unchanged by this store's existence.

`alan.engine_config.registered_secret_env_names()` (renamed from the forge-only `registered_forge_credential_env_names()`) now unions every registered engine's `forge.credential_env_name` **and** `code_quality.token_env_var`, so `_worker_env()` (`alan/claude_cli.py`) strips both classes of env-fallback name from a worker subprocess's environment — closing a pre-existing leak where `SONAR_TOKEN`, read host-side only by `alan/teams/_pr_sonar.py::sonar_ack_hotspots`, rode unstripped into worker `os.environ`. Store-only credentials (no env fallback) are never written to `os.environ` in the first place, so they need no strip entry.

### Transport injection (git-askpass, credential.helper reset)

R1.1b closes the two-identity bug the store alone doesn't: before this, git transport (clone/fetch/push) rode whatever credential helper the host's ambient git config resolved (osxkeychain on the deploy host — confirmed empirically via `git config --get-all credential.helper`, system scope), while the forge API used the engine's own token from the store above. `secrets_store.transport_env(forge_target)` is the single choke point that makes both act as one identity: it resolves `resolve_secret(forge_target.repo.slug, "transport", env_fallback=forge_target.credential_env_name)` (store-first, env-fallback, same contract as every other purpose) and returns a minimal env dict — `GIT_ASKPASS` pointing at the committed `scripts/git-askpass-alan.sh` (a static, secret-free script that echoes whichever token is named by `ALAN_GIT_ASKPASS_TOKEN` — the value is never in argv or a URL, so it's invisible to `ps` and never written to `.git/config`), the resolved token under that env-var name, `GIT_TERMINAL_PROMPT=0`, and an empty `credential.helper` reset realized as `GIT_CONFIG_COUNT=1`/`GIT_CONFIG_KEY_0=credential.helper`/`GIT_CONFIG_VALUE_0=` (git ≥2.31). Every network git call site also prepends `-c credential.helper=` to argv as a version-agnostic fallback of the same reset. Raises `MissingSecretError` — never a silent ambient fallback — when neither the store nor the env fallback resolves a value.

The choke point is wired into all three sinks that ever touch the network: `alan/slot_pool.py`'s `_run_git` (fetch call sites only — `_fetch_base`, `_fetch_existing_branch`) and its clone (`_init_slot`/`_clone_env_and_argv`); `alan/teams/_pr_push.py`'s `run_subprocess` call sites for `push_branch`, `_try_push_with_lease`, `_fetch_for_reconcile`, and `_repush_reconciled`; and `alan/teams/_pr_branch.py`'s own `run_subprocess` call site for `_git_fetch_origin`. At the time R1.1b landed, all four push/reconcile functions above lived on `alan/teams/_pr_branch.py` alongside `_git_fetch_origin` and this register described "both files" — the H5.1 shrink program's push-reconcile-cluster move relocated `push_branch`/`_try_push_with_lease`/`_fetch_for_reconcile`/`_repush_reconciled` into their own `alan/teams/_pr_push.py`, so that no longer holds. `SlotPool` skips transport injection entirely for a local (non-URL) `repo_root` — `is_remote_url()`, computed once at construction — since a local clone never contacts a credential helper; this is what lets tests exercise real local git operations without configuring any token, and is not a carve-out available in production (`_clone_source_for_engine` always returns an `https://github.com/...` URL). `alan/teams/_pr_branch.py` and `alan/teams/_pr_push.py` have no such carve-out: their worktrees are always the real deploy checkout's clone in production, so their transport calls always require a resolvable credential. `tests/test_transport_canary.py` is the CI canary: it statically proves (via AST, keyed on the git subcommand literal) that every `clone`/`fetch`/`push` argv construction across all three files calls `transport_env`, proves the empty-`credential.helper` reset defeats a simulated system-scope ambient helper (`git credential fill` with `GIT_CONFIG_SYSTEM` pointed at a throwaway file — the same resolution mechanism osxkeychain uses), and proves a pooled clone's on-disk `.git/config` never gains a `credential.helper` entry or an embedded token.

**Per-engine wiring — verified end-to-end.** Building `transport_env` is not enough on its own: every real call site must actually be handed the *workspace's own* `forge_target`, not the module-level default, or a non-default engine silently authenticates as the default engine (the two-identity bug re-opened at the call-site layer). The two production push helpers (`implementation.py::_push_changes` → `push_branch`, `implementation_fix.py::_push_fix_branch` → `push_fix_branch_with_reconcile`) now pass `forge_target=_pr_forge.forge_target_for_ws(workspace)` explicitly. `alan/routes/infra.py::_create_slot_pool_for_engine` — the constructor `_create_keyed_slot_pools` invokes at startup for every non-default registered engine — passes `forge_target=ForgeTarget.from_forge_config(config.forge)` when the engine registers a `ForgeConfig`, or an explicit `forge_target=None` when it does not.

`SlotPool.__init__`'s `forge_target` defaults to `None`, and omitting it means no credential: the pool's clone, warmup commands, and every `lease()` fetch fall back to whatever the host's ambient git credential resolution provides. `_create_slot_pool`, which builds the unkeyed default pool, passes `DEFAULT_FORGE_TARGET` explicitly, so the default pool built from a remote source keeps alan's credential; a local source resolves to `None` (`forge_port.md`, "X2.7 PR23"). A forge-less registered engine is therefore outside the same-identity guarantee until it registers a `ForgeConfig`; once it does, `SlotPool.__init__` stores one `_forge_target` used by every leg, so there is no separate per-leg wiring to miss.

**OQ2 (no long-lived transport subprocess) — verified.** Every git invocation in both sinks is a blocking `subprocess.run` call, never `Popen`; the injected credential env therefore cannot outlive the single call it was built for. Neither file enables `fsmonitor`. `tests/test_transport_canary.py::test_no_long_lived_git_subprocess_or_fsmonitor` asserts both facts statically so a future change reintroducing either would fail CI rather than silently reopening the window.

**Security review — residual-risk register.** Two residuals are accepted, not closed, by this design; both are orthogonal to the Option A (per-engine injection) vs. Option B (host identity) choice and don't favor B:
- *Same-UID at-rest read* — a worker (or any process running as the same OS user) with unscoped file read can read any `0600` secrets-store file directly; `0600` is obscurity, not isolation, against another process running as that same UID.
- *Transient-environ window* — the token lives in the transport subprocess's own environ for that subprocess's lifetime, readable by anything with the same-UID read access above (e.g. `/proc/<pid>/environ` equivalents) while the subprocess runs. Distinct from the at-rest residual above since it's a different artifact (a live process's environ, not a file) with the same reader class.

Both residuals are accepted for now and routed to the same trigger: **Keychain-backed storage must land before any non-default engine's posture is dialed to `autonomous`.** FD-passing (handing the transport subprocess an already-open file descriptor instead of an env var) is the documented reversible mitigation for the transient-environ window specifically, if it's ever judged unacceptable before the Keychain migration lands; it doesn't change the store or resolution contract.

## Control-plane guard (worker-origin protection)

`alan/control_plane.py` is a standalone, dependency-free primitive: `require_control_token(request)` 401s when the `X-Alan-Control-Token` header is absent, 403s when it doesn't match `ALAN_CONTROL_TOKEN` (compared with `hmac.compare_digest`), and 500s if the server has no token configured. It guards the two live `/api/secrets` mutators (`POST`/`DELETE`) today; the `/api/engines` mutators, the posture endpoint and the worker-origin guard of the answer endpoint reuse it unmodified — never a second implementation. Every future mutating endpoint reuses it on the same terms.

`server.py`'s `lifespan` calls `control_plane.bootstrap_control_token(state_root)` at boot, which delegates to `alan/control_token_store.py::load_or_generate`: it resolves the persisted `(value, meta)` pair against six on-disk states rather than unconditionally minting a fresh token — `secrets.token_hex(32)` is generated only when no plaintext value exists yet; a pre-existing value file with no sidecar meta record is *adopted* (its content left untouched, a fresh 30-day-from-now meta record minted for it); a revoked (tombstoned) meta record is honoured across every subsequent boot rather than resurrected into a usable token. The plaintext value lives at `<ALAN_STATE_ROOT>/control_token` (`0600`) and is set into `os.environ["ALAN_CONTROL_TOKEN"]`; its sidecar lifecycle record lives at `<ALAN_STATE_ROOT>/control_token_meta.json` (also `0600`) and carries the 30-day expiry `require_control_token` enforces at request time. This persistence is what lets a deploy-triggered restart reuse the credential already pasted into the browser instead of invalidating it. No HTTP endpoint ever returns the token value — the operator reads the file out-of-band (`cat ~/.alan/state/control_token`) and pastes it into the UI's settings, which stores it in `localStorage` and sends it as the `X-Alan-Control-Token` header on every mutating call. `alan/routes/control_token.py` exposes an unauthenticated state+deadline status projection (`GET /api/control-token/status`, never the value) plus three guarded actions (`POST /api/control-token/{extend,rotate,revoke}`) — rotate sits behind `require_control_token` itself, so an expired token cannot replace itself. This is deliberate: `alan/routes/infra.py`'s `_SPAStaticFiles` serves `index.html` as a byte-identical static file to any localhost client, worker or browser — there is no session to key a server-injected token to, so putting it in the HTML would hand it straight to any worker that curls `/`.

`alan/claude_cli.py::_worker_env()` strips the token with a single fixed-name `env.pop(CONTROL_TOKEN_ENV, None)`, distinct from the `registered_secret_env_names()` loop that strips per-engine credentials — a worker's `Bash(python:*)`/`Bash(curl:*)` reaching `localhost:8585` therefore carries no control token, and every mutating engine/secrets/posture call it attempts 401s.

**Residual-risk register.** The guard is defense-in-depth, not a hard boundary:

- *Same-UID host-env introspection* — empirically tested (`tests/test_control_plane.py::test_same_uid_subprocess_cannot_recover_control_token_via_ps`): a same-UID subprocess invoking `ps eww -p <server-pid>` against the live alan process does **not** recover a runtime-set (`os.environ[...] = token`, set well after `execve()`) value on the macOS it was tested on — `ps`/`sysctl(KERN_PROCARGS2)` report the environment snapshot captured at `execve()` time, not later in-process mutations. This is empirical, OS-version-dependent behavior rather than a documented Apple guarantee, so it stays on the register instead of being treated as closed.
- *Same-UID token-file read* — `<ALAN_STATE_ROOT>/control_token` is `0600`, but `0600` is authorization-by-UID, not isolation from other processes running as that same UID (the same framing as the R1.1 secrets-store residual above). A worker with unscoped `Read`/`Bash(cat:*)` on the host filesystem could open the file directly.
- *Chat/host-trust retention* — build/explore/workspace chat agents and the host-trust git/gh helpers (`alan/worktree.py`, `alan/teams/_pr_branch.py`) build their subprocess env from full `os.environ` by design and therefore retain the token; `_worker_env()` is the sole worker-scoped env builder, and the no-token guarantee is deliberately scoped to worker context only.
- *SPA HTML scraping* — moot: no token is ever injected into served HTML (out-of-band delivery above), so a worker curling `/` gets nothing to scrape.

Upgrade path if any of the above is later judged unacceptable (e.g. before a non-default engine is dialed to `autonomous`): a Unix-domain-socket control listener with a peer-credential check, which closes the same-UID gaps categorically instead of relying on the file/env boundary.

## Deploy-verify service-wedge recovery

`deploy_verify` (`alan/teams/deploy_verify.py`) confirms a merge went live by direct local observation, not by polling the merge's post-merge `ci-deploy` run. On the `restart_required` arm it additionally probes `/api/health` (`ALAN_HEALTH_URL`); when the live process's `served_sha()` already contains the merge but that health probe keeps failing, the service is up but unhealthy — a wedge, not a missing deploy. `deploy_verify` does not distinguish that case in its escalation message: a wedge visible during the wait simply keeps the job parked (no worker occupied) until the budget (`ALAN_DEPLOY_VERIFY_BUDGET_S`, 90 min) exhausts into the single `never_live` escalation. The escalation's diagnostic line lists the deploy workflow of the workspace's own engine (snapshot, then registry record, then the default engine's `ci.deploy_workflow`), not a hard-coded workflow name, and an engine that configures no deploy workflow gets no lookup at all — see `docs/architecture/deploy_verify.md`'s "Deploy workflow per engine". Recover manually, before or after that escalation fires, with:

```bash
launchctl kickstart -k gui/$(id -u)/ai.alan
```

This forces the process to restart without re-reading the plist; confirm recovery with `curl -sf http://127.0.0.1:8585/api/health`. If the service still doesn't come up, check `~/.alan/logs/alan.error.log` before trying a full bootout/bootstrap cycle. Escalation mechanics and the merge/forge-race wait budget are documented in `docs/architecture/deploy_verify.md`.

## Host toolchain licence gate

**Symptom.** A macOS major upgrade re-arms the Xcode licence gate on a fleet host. Every tool that resolves through the Xcode toolchain — including the system `git` and `python3` the fleet depends on — starts refusing to run. Workers fail with errors that read as scope or code problems rather than a host problem, and workspaces park or escalate for the wrong reason; the real cause is otherwise found only by accident. This recurs by design, because automatic OS updates are a standing decision on these hosts.

**Detection.** `alan/worker_liveness.py::probe_host_toolchain()` runs a version-probe against `git` and `python3` on every 30-minute health sweep (`docs/architecture/health.md`'s `host_toolchain` finding kind). A gated host surfaces as a critical, `deep_link` finding on `/api/health` within one sweep, naming both resolved binary paths, the failing tool's own error message, and the recovery command.

**Recovery command:** `sudo xcodebuild -license accept`

This string is the probe's **fallback constant** (`alan/worker_liveness.py::_LICENSE_RECOVERY_FALLBACK`) — the finding itself prefers whatever `sudo …`-prefixed line the failing tool's own error output contains, and falls back to this literal only when no such line is present. It has not been verified against a live gated host (no host in this pipeline has ever been in that state to test against); treat it as a documented best-effort value, not a confirmed quote.

## Tuning knobs

- `ALAN_DISPATCHER_CONCURRENCY` (default 6) — parallel worker threads, shared across every workspace and engine. Same-workspace jobs are additionally bounded by the intra-workspace cap (`alan/queue.py`), which is **not** unconditional serialization: `INTRA_WORKSPACE_CAP` = 1 (strictly serial) only when no slot pool is active, as in CI and local dev, while production runs a pool and therefore `INTRA_WORKSPACE_CAP_POOLED` = 2 — one workspace can occupy two of these worker threads at once, each in its own isolated clone. Legacy single-task workspaces stay serial either way. See `dispatcher_concurrency.md`'s "Intra-workspace fan-out cap". The default of 6 is sized against the per-worker caps in "Fleet worker priority and parallelism caps" below. A value in `~/.alan/secrets.env` always wins over the code default, and that file is untracked, so the number in code is only ever the recommendation until an override is cleared by hand. Whether a given fan-out actually keeps the host responsive stays a manual, live-host observation the operator makes (not automatable — see below). See `dispatcher_concurrency.md`.
- `ALAN_USAGE_LIMIT_SAFETY_BUFFER_SECONDS` (default 120) — safety margin `alan.usage_limit.parse_reset_time` adds to the parsed usage-limit reset time; set to `1` in E2E (`playwright.config.ts`) so `usage-limit-pause.spec.ts` finishes fast. See `queue_and_dispatcher.md`.
- `ALAN_LOG_LEVEL` (default `INFO`) — root logging level for `python -m alan`.
- `ALAN_HOST` / `ALAN_PORT` (defaults `127.0.0.1` / `8585`) — bind override chain: explicit CLI flag > env var > default; empty/whitespace env is unset; a garbage `ALAN_PORT` value falls back to the default. Both are read by `alan/bind.py`. A non-loopback effective host is refused at startup. See "Bind host/port override chain" above.
- `ALAN_AUTO_CONTINUE_DISABLE` (default unset/off) — fleet-wide kill switch for `alan.auto_continue`: set to `1` in `~/.alan/secrets.env` to stop every project's `autonomy=auto_continue` dial from dispatching unattended, independent of the per-project setting. Unlike the `ALAN_*_ROOT` vars, this is not a state-isolation surface (it gates production dispatch behavior, not where test state lives), so it is not threaded into `alan/web/playwright.config.ts`'s `serverEnv`. See `inbox.md`'s "P7.1 (partial) — per-project auto-continue".
- `ALAN_DEPLOY_VERIFY_MERGE_RACE_BUDGET_S` (in-code default `300`) — how long `deploy_verify` waits when a just-merged PR's `mergedAt` is momentarily unavailable (GitHub eventual consistency, or a `gh` call failure) before treating it as a genuine problem and escalating; a closed-unmerged or still-open PR escalates immediately without consuming this budget. Deliberately not threaded into the plist, CI workflow env, or `serverEnv` — production always runs the in-code default. See `docs/architecture/deploy_verify.md`.
- `ALAN_DEPLOY_VERIFY_BUDGET_S` (default `5400`, 90 min) — repurposed by the event-driven, local-observation verification rebuild: no longer a queued-CI-plus-restart-plus-settle wall-clock guess, now "how long before we conclude the wake event is never coming." Verification itself no longer occupies a worker or burns this budget in-process while waiting — `deploy_verify` parks the job on its `GateRecord`, either `path="awaiting_restart"` (mergedAt still unresolved, woken by the next service restart via `deploy_gate_sweep.promote_covered_jobs`) or `path="awaiting_live"` (mergedAt known, waiting for local observation to confirm the merge is live — additionally woken every 60s by an in-process periodic sweep on the dispatcher tick that promotes purely from local probes, `deploy_observe.observe(merge_sha, health_url=None)` with `health_ok` forced `True`, issuing no `gh` subprocess and no network health probe, so it does not depend on another restart arriving), so setting this generously costs nothing either way. `ALAN_DEPLOY_VERIFY_POLL_INTERVAL_S` — the poll-loop cadence knob this replaced — is gone entirely, along with the in-process poll loop it configured; there is nothing left to poll. Budget exhaustion collapses to exactly one `never_live` escalation (`gh run list` diagnostics are attached as detail only, on the escalation path, never on the wait path) — see `docs/architecture/deploy_verify.md`. Because the `awaiting_restart` stage's wake-up event still depends on the restart actually happening at all, `KeepAlive`/`RunAtLoad` on the `ai.alan` launchd job (`deploy/ai.alan.plist`) remains load-bearing for more than service liveness — it is what guarantees that first-stage event eventually fires, even after a crash unrelated to the deploy itself; the `awaiting_live` stage's periodic sweep does not share that dependency.
- `ALAN_COMPLETENESS_THRESHOLD` (default `0.7`, read via `alan.teams._base.float_env`) — the minimum verifier-reported `COMPLETENESS` score (see `alan.teams._orchestrated.parse_verifier_metrics`) an orchestrated team's (research / opportunity_scout) run can carry without attaching a blocking `low_completeness` OpenQuestion. Below threshold, the workspace parks `awaiting_input` with the score and gaps surfaced as a structured park `Blocker` (see `docs/architecture/router.md`) and on `Handover.verifier_completeness`/`verifier_gaps` (schema 1.16, `docs/architecture/handover.md`). Garbage/unset values fall back to the default per the standard `float_env` contract; unparseable verifier output leaves the gate fully inert regardless of this knob.
- `ALAN_DETACHED_WORKERS` (default `auto`; `auto` / `on` / `off`) — whether a journal-mode team worker starts in its own process session (`start_new_session=True`) and survives a service restart. `auto` follows whether a working-area pool is configured (`ALAN_SLOT_POOL_ROOT`) — production resolves `on`, everywhere else (no pool: CI, e2e, local dev/pytest) resolves `off`. `on` forces the launchd-survival path. **Rollback**: set `ALAN_DETACHED_WORKERS=off` in `~/.alan/secrets.env` and bounce the service (`launchctl kickstart -k gui/$(id -u)/ai.alan`) — sub-minute. Off means the *next* boot terminates every currently-surviving detached worker by process group (one log line per kill, see [worker_records.md](worker_records.md)) and every subsequent spawn goes back to the pipe/pre-detachment path; it does not touch a worker that has already completed. **Reservation exposure**: a slot reserved for a detached survivor is not leasable to another job until its record probes dead — a stuck/wedged detached worker therefore holds its working area, visible via the reservation staying in the slot pool's state past its normal TTL (it re-arms instead of expiring while the record still probes live; see [worker_records.md](worker_records.md)). The resolved mode and why are logged once at boot (`detached_mode.log_resolved_mode()`). Classified `EXCEPTED_CONFIG` (ops tuning knob), pinned to the literal `"off"` in `alan.claude_cli._worker_env` and in `alan/web/e2e/fixtures/server-env.ts` — the pin is load-bearing for a service forced on, since `auto` already resolves `off` inside a spawned worker's own environment (the pin exists so a worker subprocess can never inherit `on` from the service's ambient environment even when the service itself is dialed on). `auto`'s predicate reads `ALAN_SLOT_POOL_ROOT` — the same variable used to redirect the slot pool's state-isolation root — so any test or environment that sets it purely for isolation, without meaning to opt into pooling, resolves `auto` to `on` for that process; harmless as long as the two pins above stay in place, but worth knowing before reusing that variable for isolation elsewhere.

## Fleet worker priority and parallelism caps

`alan/fleet_load.py` bounds how much of the host a single fleet worker's gate run can claim — this is what actually addresses the host saturation an uncapped fleet fan-out produces; reducing the fan-out alone only reduces how many workers run at once, not how much each one claims. The module is deliberately dependency-free (it imports nothing from `alan/`) and carries two independent mechanisms, both applied only on the fleet spawn path — interactive chat turns (`run_chat_turn`) are untouched, at normal priority and with neither cap:

- **Scheduling priority.** `_spawn_streaming_cli` (`alan/claude_cli.py`) calls `apply_fleet_priority(proc.pid)` — `os.setpriority(os.PRIO_PROCESS, pid, FLEET_NICE_DELTA)` — parent-side, immediately after `Popen` returns and before writing to the child's stdin. This runs on the same code path the detached (`start_new_session=True`) branch takes, so a worker that survives a service restart carries the reduction too, and every descendant process the worker forks (test runners, build tooling) inherits it via ordinary Unix priority inheritance. Two alternatives were rejected: `preexec_fn` forks Python inside a thread-holding server process (a deadlock hazard), and wrapping argv in `/usr/bin/nice` corrupts the `ps -o command=` snapshot `alan/worker_records.py`'s `_identity_matches` compares against, which would misclassify live detached workers as dead.
- **Test-suite parallelism caps.** The fleet branch of `_worker_env` prepends `-n 2` to any existing `PYTEST_ADDOPTS` (an explicit CLI `-n 0` still wins — pytest resolves the last `-n` flag across the combined ini-`addopts` + `PYTEST_ADDOPTS` + CLI-args list, and ini addopts resolve first) and sets `VITEST_MAX_WORKERS=2`; `alan/web/vitest.config.ts` reads the latter into `test.maxWorkers`, falling back to Vitest's own default when the variable is unset. Neither variable is `ALAN_*`-prefixed, so neither enters `tests/env_var_classification.py`'s isolation/excepted-config table — these are fixed literals, not operator dials, and there is no env var to raise or lower them with.

**Derivation.** The caps are sized against the fan-out value above (6). The arithmetic below is deliberately stated as an oversubscription, not as a comfortable margin — an earlier revision of this section claimed the latter by counting only `max(backend_cap, frontend_cap)`, which is wrong twice over and is corrected here.

The implementation and implementation-fix prompts instruct a worker to run its gates "in parallel, as parallel Bash tool_uses in one turn" (`alan/teams/implementation.py`, `alan/teams/implementation_fix.py`), and the default engine declares 16 `gate_commands`. The backend and frontend suites therefore **overlap** rather than alternating, and each suite also has its own controller process on top of its workers. A single worker at the peak of a gate turn holds roughly: `pytest` (1 controller + `FLEET_PYTEST_WORKER_CAP` = 2 workers), `npm run test:coverage` (1 controller + `FLEET_VITEST_WORKER_CAP` = 2 workers), the 14 remaining largely single-process gate commands, and its own `claude` CLI — about 21 processes. Across six simultaneously gating workers that is roughly 126 processes competing for one host's cores.

What the caps actually buy is a bound on the **dominant CPU-bound term**, not a process count under the core count. Uncapped — the configuration that saturated a fleet host before the caps landed — a worker's two test suites alone spawned `pytest -n 6` (this repo's `addopts`) plus Vitest's default of roughly one worker per core, about 21 test processes per worker, at normal scheduling priority. Capped, those same two suites spawn 6. The other 14 gate commands are single-process and mostly short-lived; they were never the saturation driver.

So the accepted position at fan-out 6 is: nominally oversubscribed several times over at the peak, mitigated by (a) that ~3.5x reduction in the test-worker term, (b) every fleet process running at `FLEET_NICE_DELTA` below normal, so interactive use preempts them, and (c) the peak requiring all six workers to be inside a full gate turn at the same instant — a small fraction of a worker's wall clock, most of which is spent blocked on the Claude API. That is a stated, accepted margin, not a proof of safety; the paragraph below says why no proof is available.

**Rollback lever, in preference order**, if the host does not stay responsive: drop `FLEET_PYTEST_WORKER_CAP`/`FLEET_VITEST_WORKER_CAP` to 1, which re-bounds the dominant term at the cost of roughly doubling each gate run's wall clock; then reduce the fan-out via `ALAN_DISPATCHER_CONCURRENCY` in `~/.alan/secrets.env`. This is what "the bound is sized from a stated principle, not picked in isolation" means in practice: changing the fan-out requires redoing this derivation against the new value, not just bumping a number.

This is enforcement, not guidance: unlike the verification-role prompt hints on reducing duplicate full-suite runs, these two mechanisms are applied unconditionally on every fleet spawn and cannot be skipped by a worker choosing not to follow instructions. Whether this is enough — i.e. whether two workspaces in gate-heavy phases concurrently actually keep the host responsive — is a live-host observation, not something CI can assert or a proxy metric can stand in for.

## Logs & state

Logs: `~/.alan/logs/alan.log` and `~/.alan/logs/alan.error.log` (`ALAN_LOGS_ROOT` override). The dispatcher logs `team start` / `team done` at INFO and `job failed: … error=<reason>` at WARNING; terminal job failures also append to `~/.alan/logs/job_failure_audit.jsonl` (`queue_and_dispatcher.md`); failed `claude` subprocess output is logged at WARNING (`claude_cli_streaming.md`).

**Host log timestamps are UTC.** `alan/__main__.py::_configure_logging` sets `logging.Formatter.converter = time.gmtime` as a class-attribute override, before `uvicorn.run(...)`. A root-logger-level fix (e.g. configuring only the `alan` logger's own formatter) would have missed uvicorn's own handlers, which `uvicorn.run` installs from its own `LOGGING_CONFIG` independently of `logging.basicConfig` — the class attribute is what makes every handler, uvicorn's included, format in UTC. Before this change, host log lines were in host-local time while every structured audit JSONL (`impl_audit.jsonl`, `pr_merge_audit.jsonl`, the new `gh_quota.jsonl` below, …) was already stamped `timestamp_utc` — the skew meant a timeline built from both streams had to be manually offset, and a past investigation double-counted incidents across the mismatched clocks. `alan.log` / `alan.error.log` and every `*_audit.jsonl` file are now directly correlatable by timestamp with no offset.

**GitHub API quota telemetry (`gh_quota.jsonl`).** `alan/teams/_forge_quota.py` records one `QuotaSample` per outbound GitHub GraphQL call the system already makes — today that is the PR-feedback fetch in `alan/teams/_pr_feedback.py` (call site `pr_feedback_graphql`), which now requests `rateLimit{limit,cost,remaining,resetAt}` alongside its existing query so quota costs zero extra calls to observe. Each line under `logs_root()/"gh_quota.jsonl"` (`ALAN_LOGS_ROOT` override, same as the logs above) is a JSON object: `resource` (`"core"` or `"graphql"`), `call_site`, `limit`, `cost`, `remaining`, `reset_at` (epoch seconds or `null`), `outcome` (`"ok"` / `"rate_limited"` / `"transient"` / `"error"`), plus the shared `timestamp_utc` every `append_jsonl_audit` writer stamps. `cost` and the other quota fields are nullable: a failed call (timeout, non-2xx `gh` exit, or a GraphQL `errors[]` payload) is still recorded as a "null-cost" event so failure volume by call site is visible, but it cannot tell you how much quota that specific call actually spent — only a successful call with a parsed `rateLimit` block carries a real `cost`. `core` and `graphql` are GitHub's two independent rate-limit pools; nothing in this build queries the REST `core` pool, so every sample recorded today has `resource: "graphql"`. The file rotates in-module (no `retention.py` involvement — that sweep only covers `.stream.jsonl` files and archived workspace directories, and this ledger writes on every merge poll rather than once per implementation, so it grows materially faster): `_forge_quota.record_quota_sample` renames the file to `gh_quota.jsonl.1` once it exceeds 32 MiB, keeping exactly one backup generation. To answer "which call site spent what share of the quota" after an incident:

```bash
jq -s 'map(select(.cost != null)) | group_by(.call_site) | map({call_site: .[0].call_site, total_cost: (map(.cost) | add), calls: length})' ~/.alan/logs/gh_quota.jsonl
```

**Rate-limit pauses are reset-derived, not a fixed guess.** `alan.teams._forge_errors.forge_rate_limit_reset_at(payload=None)` now parses the reset time out of whatever response text is available (`alan.teams._forge_quota.reset_at_from_text`, which recognizes both a quoted `"resetAt":"<ISO8601>"` field and a bare `"reset"`/`"resetAt"` epoch-seconds-or-milliseconds field) and clamps the result to `[now, now + 3600s]` — a parsed value from garbled or adversarial text can extend a pause by at most an hour, and can never produce a pause shorter than zero. When no reset time is parseable from the available text (most call sites today, since GitHub's `gh` CLI rarely echoes a reset timestamp on failure), it falls back to the previous fixed 900s constant unchanged. Every `raise_for_infra` rate-limited call site inherits this automatically; `alan/teams/_pr_branch.py`'s `_handle_pr_view_failure` and `alan/teams/_pr_feedback.py`'s feedback fetch pass their own `stderr`/rc-failure text explicitly.

**Forge-health headroom is in-process, restart-cold state.** `alan.teams._forge_quota`'s last-known-sample registry (`_LAST`, guarded by a module-level lock since the dispatcher runs concurrent merge polls as `ThreadPoolExecutor` threads in one process) is pure in-memory state — nothing persists it across a process restart. `alan.teams.triage_pregate.gather_forge_degraded` surfaces a `blocker_reason="forge_low_headroom"` (`is_blocked=False`, so it never engages the queue-wide pause — telemetry only) finding once remaining quota drops under 10% of the limit and no active rate-limit pause is already in effect; `alan/health.py` renders it as a `medium`/`deep_link` finding via the same `forge_degraded` kind the rate-limited state already uses. Every auto-deploy restart therefore clears this signal until the next successful merge-poll GraphQL call repopulates it — a cold headroom reading after a deploy is expected, not a bug.

State: `~/.alan/state/` (`ALAN_STATE_ROOT` override), e.g. `pr_<n>_acked_comments.json` — the locally-maintained acked set for PR-level Copilot comments (GitHub has no `resolveIssueComment` mutation); safe to delete a file to force `pr_merge` to re-block on its comments. See `pr_iteration_pipeline.md`.

**Supervised driver loops** ([driver_loops.md](driver_loops.md)) run as a standalone daemon thread, gated on the same `ALAN_DETACHED_WORKERS` dial as detached fleet workers — nothing spawns unless this instance is production (or otherwise resolves the dial `on`). Run records live at `~/.alan/state/driver_loops/<name>/runs/`, logs at `~/.alan/logs/driver_loops/<name>/`, and PAUSE files at `~/.alan/driver_loops/pause/<name>.pause`. Every registry entry in `config/driver_loops.d/` ships `enabled: false`; enabling one, provisioning the two issue drivers' dedicated clones, and confirming a zero-permission-denial live run is the owner's own post-merge rollout check, not a CI gate.

## Operator terminal

The Operator page runs one interactive Claude Code session inside a tmux session on a private socket. Design, security model and accepted risks: [operator_terminal.md](operator_terminal.md). This section is the operational side.

- **Prerequisites.** `tmux` (installed by `scripts/setup_macos.sh` with the other Homebrew formulae), `claude` and `git` on the session's allow-listed `PATH`, and detached mode resolving to `on` (`ALAN_DETACHED_WORKERS`, above). A missing prerequisite never shows a broken terminal: the page reports "unavailable" with the named cause (`tmux_missing`, `claude_missing`, `git_missing`, `detached_mode_off`, `checkout_clone_failed`). On a setup install nothing needs a manual step.
- **Where the session runs.** A separate clone of the install's own `origin` at `<install-parent>/<install-name>-operator`, beside the install checkout and never inside it, so the deploy's `git reset --hard` + `git clean -fdx` never touch it. alan creates it the first time a session is needed; there is no setup step for it, and a first clone can take a while. A clone that fails is reported as `checkout_clone_failed` and no session starts.
- **How it is updated.** At session start, and only when no session is live: `git fetch` then `git merge --ff-only @{upstream}`, never a reset, so local work left in the checkout survives. A failed update is shown as a warning on the page and the session still starts. A replace ends the old session before the update runs.
- **Restart survival.** The tmux server is a daemon on a socket under the state root (`ALAN_STATE_ROOT`, default `~/.alan/state/operator/`), so a service restart or deploy does not end the session, and the service keeps no session state in memory. Reattachment happens when the page is opened, not at boot. A tmux server that was killed, or a machine reboot, ends the session; the page then shows no session and the next start begins a fresh one.
- **Sharing Claude Code memory with the operator checkout (optional, manual, never automated).** Claude Code keeps its per-project memory under `~/.claude/projects/`, in a directory named after the checkout's path, so the operator checkout starts with none of the memory the install checkout has built up. To share it, run `claude` once in the operator checkout so its project directory exists, list `~/.claude/projects/` to find the two directories, move aside any `memory` directory inside the operator checkout's, and link the install checkout's in its place:

  ```bash
  ln -s ~/.claude/projects/<install-checkout-dir>/memory ~/.claude/projects/<operator-checkout-dir>/memory
  ```

  Then start a session and confirm it sees the shared memory; if it does not, remove the link. Neither alan nor setup does this for you, and skipping it costs nothing but that context. A shared memory is read by a session that holds your full authority, so share it only if you would paste its contents into that session.
