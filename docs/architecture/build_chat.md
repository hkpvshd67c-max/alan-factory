# Build Chat architecture

## Overview

A third isolated chat family under `/api/build-chat` — alongside Create Task (`/api/chat`) and Open Chat (`/api/open-chat`) — for the Build home-entry mode. The user discusses what they want built, distils it into an editable build brief, then dispatches an `implementation_plan` workspace. Realises ADR `docs/architecture/build_mode.md` decisions D06–D17 (the Build button + tabbed surface; Decision area 1 / completion redefinition is a separate sibling task).

## Backend isolation

`alan/build_chat.py` is a thin shim over the shared `alan/_chat_core.py` (session model, storage, locks, startup reconcile, parametrized by a `ChatCoreConfig`); it re-exports the `BuildChat*` names and stores sessions in `~/.alan/build-chat-sessions/` (configurable via `ALAN_BUILD_CHAT_SESSIONS_ROOT`). `BuildChatSessionLocks` subclasses the shared `ChatSessionLocks` (`threading.Lock`), deadlock-free under the `run_in_threadpool` turn machinery. The session core and the chat surfaces are genuinely shared, not cloned — `_chat_core.py` is the single implementation used by all surviving chat families.

`alan/routes/build_chat.py` registers an `APIRouter` at `/api/build-chat` whose endpoints are thin wrappers over `alan/routes/_chat_router.py` (bound to a `build-chat` `ChatRouterCtx`). **P6.2** deleted the build-only `/extract` endpoint (`parse_build_extract`/`BuildExtractError`) — build-chat's dispatch now runs through `POST /sessions/{id}/propose`, the SAME `_chat_router.run_dispatch_proposal` helper explore-chat uses (see `docs/architecture/chat_shared_mechanics.md`'s "Commitment gate as an action" section). This is the ONE proposal-generation path: `run_dispatch_proposal` sends the shared `DISPATCH_PROPOSAL_SENTINEL`, parses the reply into the shared `DispatchProposal` model, and merges a server-side `scan_predispatch` scan into `scope_audit` — build-chat's closure passes `title=""` and `description=<the saved brief content>` (the proposal's own title doesn't exist yet at scan time) with `exclude_task_id=None` (no workspace exists yet to exclude).

Stopping an in-progress build-chat turn and sending a redirected message next is shared, not build-chat-specific behaviour: resume is decided solely from the session's recorded `cli_session_id` (never inferred from transcript shape), `POST /sessions/{id}/interrupt` always returns `204`, and a stopped turn lands as a `turn_stopped` SSE event with an `interrupted=True` transcript entry rather than an error — see `docs/architecture/chat_shared_mechanics.md`'s "Stop-and-redirect: recorded resume, the `TurnEntry` lock lifecycle, and `turn_stopped`" section for the full mechanics, all of which live in `alan/_chat_core.py`/`alan/routes/_chat_router.py` and apply identically here.

## Prompt contract

`alan/claude_cli.py` exports:
- `_DEFAULT_CHAT_ALLOWED_TOOLS` (used here and by explore-chat, since both leave `ChatRouterCtx.allowed_tools=None`) pre-approves `Bash(gh issue view:*)` (`CHAT_ISSUE_READ_TOOL`, `alan/claude_cli_grants.py`) alongside the existing `gh pr list`/`gh pr view` grants — a build-chat user can reference a private GitHub issue in the bound repository by number, and the assistant reads it in the same turn. No `gh issue list`/`create`/`comment`/`edit` is granted. The read-only posture is the static constant `BUILD_NO_IMPL` (`alan/claude_cli_grants.py`): a head, `_BUILD_NO_IMPL_HEAD`, whose allowed-tools line advertises this ability and which composes the shared `CHAT_ISSUE_SCOPE_CLAUSE` — a session reads an issue by number or by a pasted URL naming its own bound repository (extracting the trailing issue number itself and calling `gh issue view <number>` in the same turn), and declines an issue referenced from a different repository rather than fetching it; this is prompt-level scoping only, with no URL parser or validator. The head is followed by the static `PREP_CHAT_ATTACHMENT_CLAUSE` (catalogue segment `chat_prep_chat_attachment`), which tells the assistant that a pasted preparation-chat link has already been read by the service and appended to the user's message as a `<preparation_chat>` block, explains the `read`, `other_repository` and `not_found` outcomes and the `truncated: K of N earlier messages omitted` line, and forbids fetching the link, calling localhost or reading the state directory. `format_build_system_prompt` embeds `BUILD_NO_IMPL` unconditionally: nothing in the prompt depends on `prep_chat_origin` (see [prep_chat.md](prep_chat.md#reading-a-pasted-preparation-chat)). The constants (with their `EXPLORE_NO_IMPL` sibling — see `explore_chat.md`) live in `alan/claude_cli_grants.py` rather than `alan/claude_cli.py`, which keeps `claude_cli.py` under its shrink-only 1410-line size-ratchet pin (`tests/size_baseline.py`) while these prompt constants grew a shared issue-read clause.
- `BUILD_SUMMARIZE_SENTINEL = "SUMMARIZE_BUILD"` — sent by the Summarize button; distils a behaviour-level build brief that deliberately omits file/module/function names (choosing those is the implementation_plan team's job).
- `DISPATCH_PROPOSAL_SENTINEL = "EXTRACT_DISPATCH_YAML"` — shared with explore-chat (P6.2); sent before dispatch, the assistant replies with a YAML document shaped `status: ready` / `proposal: {team, title, rationale, acceptance_clauses, recorded_clauses, counter_case}` (team is always `implementation_plan` for this door) or `status: need_more_info` / `questions: [str, ...]`.
- `format_build_system_prompt(shop_stats: str = "")` — read-only "build planning assistant" posture; no team catalog, no scope-audit gate. Composes a `## UX lens` section (`_CHAT_UX_LENS`) between the read-only posture block and the summarize/dispatch contracts, prompting the user's build brief to weigh visual hierarchy, empty/loading/error states, keyboard & focus, WCAG-AA parity, and reuse of shared UI primitives when the request touches the web UI, grounded in `docs/DESIGN_SYSTEM.md` — the assistant is also told to say explicitly in its answer that it is applying the lens. `_CHAT_UX_LENS` is a single `claude_cli.py`-layer constant shared verbatim across this build-planning prompt and the `brainstorming`/`architecture` explore consultants (gated by `ConsultantInfo.carries_ux_lens`, see `explore_chat.md`) — there is no per-surface duplication of this wording left. It is a `claude_cli.py`-layer sibling of the `implementation`/`implementation_fix` teams' `UX_LENS` constant and the `implementation_plan`/`architecture`/`brainstorming` teams' `PLANNING_UX_LENS` constant (both in `alan/teams/_base.py`), deliberately not imported here because `claude_cli.py` sits below `teams/` in the import-linter layering — each layer defines its own lens text rather than reaching across the boundary. `shop_stats` is an optional pre-assembled read-only block (see below) — omitting it (or passing `""`) keeps the prompt byte-identical to before this argument existed, since `claude_cli.py` sits at the bottom of the import-linter layering and cannot gather the block itself.

## Measured shop stats (P5.1)

`alan/shop_stats.py::assemble_shop_stats_block(queue)` is a pure read-model assembler that sits high (near `routes`/`health`, unconstrained by the import-linter layers contract, like `alan/health.py` and `alan/digest.py`) so it can read state the bottom-layer `claude_cli.py` cannot reach. It formats four fleet-level signals — the fixed learning metrics (`alan.health.load_learning_metrics`), fleet health/CI/deploy state (`alan.health.load_health_state`), the fleet merge-gate recovery rate (`alan.health.load_merge_gate_recovery`, reading the triage sweep's `merge_gate_recovery_v1` queue-meta blob), and restart recovery (`alan.health.load_restart_recovery`) — into one plain-text block, each signal stamped "as of &lt;computed_at&gt;". `load_merge_gate_recovery`'s accessor lives in `alan/health.py` next to the fleet-health accessors, but the value it returns never reaches `HealthState`, the verdict, or `blocked_count` — the merge-gate blob is computed and stored by the triage sweep independently of `compute_health_state`, and this read chain feeds only the shop-stats block above. Assembling it performs **zero** per-prompt trajectory derivation, audit-log scan, or git invocation — it only reads pre-aggregated slow blobs plus cheap live `queue.get_meta` calls, so it adds no new file-descriptor pressure. An all-missing sweep degrades to four "not enough data yet" lines rather than fabricating numbers or leaking a literal `None`. It deliberately excludes the per-brief collision-check result (that stays session-scoped via the existing `collision_run_summary`, since collision needs a concrete brief that doesn't exist yet when this block is assembled) and the P3.1/P3.4 process-trust signals (deferred).

**Merge-gate recovery is windowed to 30 days.** `alan.learning_metrics.merge_gate_recovery_rates(text, *, now, window_hours=MERGE_GATE_WINDOW_HOURS)` reuses the same `_row_within_window` helper `restart_recovery_counts` already uses, but discovers class names from every row in the audit log (so a class that has gone quiet still renders) while gating only `total`/`recovered` behind the window; every row also bumps a `lifetime_total` counter that is never windowed. `alan.teams.triage._compute_merge_gate_recovery_safe` threads its own already-computed sweep `now` through (the computation never reads the clock itself) and stamps `window_hours` into the stored `merge_gate_recovery_v1` blob alongside `rates`/`computed_at`. `alan/shop_stats.py` renders the period every line covers: `_window_label` reads `last 30d` when `window_hours` is a stored positive number, and falls back to `all history` for a blob written before this change (no migration — the fallback is what keeps the prompt truthful for the up-to-~30-minute gap between deploy and the next triage sweep). A class with zero rows inside the window renders `no measurement in last 30d (lifetime N)` instead of a fabricated `0.0%`; per-class percentages below `_MIN_RATE_SAMPLES = 5` render as raw counts (`recovered/total (below minimum sample size)`) instead of a rate a tiny sample can't support, while the overall line keeps its percentage. Windowing happens once, in the triage sweep, not at render time — `assemble_shop_stats_block`'s zero-per-prompt-scan invariant (above) is unaffected.

**Hard ceiling: `MERGE_GATE_WINDOW_HOURS` (`alan/learning_metrics.py`) must never be widened to reach 2026-06-30 through 2026-07-02.** A cluster of test-fixture rows sits in the production `merge_gate_audit.jsonl` with timestamps in that range; the 30-day (720-hour) window keeps them permanently outside every computed rate without needing to identify or filter them by row. Check any proposed widening against those two dates first, not against a day count computed today — a day count is only true on the day it's written. `tests/test_triage_merge_gate_window.py` is the executable guard: it asserts a row timestamped `2026-07-01T12:00:00+00:00`, evaluated at a sweep `now` of `2026-08-30`, contributes only to `lifetime_total` and not to `total`/`recovered`.

`alan/routes/build_chat.py` loads the queue at the top of each turn-driving endpoint (`messages`, `propose`, `summarize`, and the session `GET`), assembles the block via `run_in_threadpool`, and builds a per-request `ChatRouterCtx` (`dataclasses.replace(_CTX, system_prompt=...)`) that closes over the assembled string — the shared module-level `_CTX` itself stays fixed since `ChatRouterCtx.system_prompt` only receives the session. The same block is fed as plain data into the PM ritual's daily digest (`alan.digest.render_digest(..., shop_stats=...)` → `DigestDoc.shop_stats`, serialized symmetrically by `digest_to_dict`/`digest_from_dict`). This is read-and-cite only: no gate, ordering, or dispatch decision reads these numbers back.
- `alan.dispatch_proposal.DispatchProposal` (`team`, `rationale`, `instructions`, `scope_audit`, `counter_case`, plus the optional `title`/`acceptance_clauses` pair added in P6.2 — see [dispatch_proposal.md](dispatch_proposal.md) for the contract's own owner page) is now the ONE proposal model both doors validate against — build-chat's `/extract` and its bespoke `BuildExtractReady`/`BuildExtractOpenQuestions`/`BuildQuestion` models are gone. `title` and `acceptance_clauses` are the new-workspace discriminant: a model-validator (`_validate_new_workspace_shape`) enforces `title is not None ⟹ team == "implementation_plan"` and `acceptance_clauses non-empty ⟹ title is not None`, so a proposal can't mint acceptance clauses without a title, or claim a title for a team other than `implementation_plan`. `acceptance_clauses` uses `FreeTextList` (from `alan/yaml_normalize.py`) rather than `list[str]` — a Pydantic `BeforeValidator` that runs each item through `recover_item`, reconstructing dict-mis-parsed YAML items (e.g. `{"Clause": "detail"}` → `"Clause: detail"`) back to their intended text, so bare colon-space acceptance clauses the LLM emits never cause a 422. The build door's dispatch-contract prompt steers the model toward quoted scalars or `|` block scalars for clauses that contain a colon, reducing malformed YAML in the first place. The same `recover_item` primitive is used by `require_str_list` in `alan/routes/_deps.py`, so the same normalisation covers the task-chat surface without per-surface duplication.

`acceptance_clauses` is the agreement-time mint point (Phase 1a): the shared `EXTRACT_DISPATCH_YAML` contract instructs the build-door assistant to emit, on `status: ready`, the agreed definition-of-done as a list of plain behaviour-level outcome strings (default `[]`). This is the **only** agreement surface that mints clauses in this phase — the Create Task chat (`/api/chat`) is deliberately unchanged and still requires a `test_ref` on any requirement it emits. The frontend forwards `acceptance_clauses` to `POST /api/workspaces` as `requirements: [{text}]` (no `test_ref` → unbound clauses): the shared `useDispatchProposalFlow` hook's proposal-panel `onConfirm` (see "Frontend" below) passes `proposal.acceptance_clauses` into `useDispatchWorkspace.dispatchWorkspace`, which threads them to `api.createWorkspace(..., acceptanceClauses)` (mapped to `requirements`). The server mints each clause's stable `id` and never blocks completion on them (see `docs/architecture/acceptance_gate.md`). `RequirementsChecklist` is keyed on the clause `id` (not `test_ref`, now nullable) so unbound clauses render.

**Recorded clauses.** The same contract also asks for a parallel `recorded_clauses` list (default `[]`): agreed outcomes whose only possible evidence is prose — a docs passage or the change description — never anything a test, CI or the running system can prove. The contract carries one budget-guidance sentence (keep the blocking list to about a dozen clauses; prefer splitting an item over compound "X and Y and Z" clauses). The budget is advisory only: no host-side code counts clauses, refuses a proposal or bounces an over-budget one, because a hard ceiling rewards compound clauses and can loop an unattended driver. The frontend threads `proposal.recorded_clauses` through `useDispatchProposalFlow.commit` → `useDispatchWorkspace` → `api.createAndDispatchWorkspace(..., { recordedClauses })`, and `deriveRequirementsFromAcceptanceClauses` sends blocking clauses with no `kind` and recorded clauses with `kind: "record"`. `DispatchProposalFields` renders the proposal in two groups: `Blocking (n)` always (the count is in the heading text, and the existing `dispatch-proposal-acceptance-clauses` testid stays on that list) and `Recorded (n)` only when at least one recorded clause exists; the section is absent when both lists are empty. The count is the length of the proposal's blocking list with no view-side dedupe, so an intra-list duplicate can inflate it by one — the host collapses it at creation. `RequirementsChecklist` marks a record clause with a neutral "prose evidence" chip carrying its own accessible name and leaves a blocking clause unmarked. The same view serves the explore chat, whose contract never asks for recorded clauses. See `acceptance_gate.md` for the accepted risk that a model can file a behavioural outcome as recorded.

## Devil's-advocate counter-case (P5.2) and the commitment gate (P6.2)

`alan/scope_audit.py::CounterCase` (sibling of `ScopeGapFinding`) is a required, non-nullable nested model with three bounded (1–2000 char) string fields: `against` (the single strongest argument against committing to this scope now), `cheapest_80` (the cheapest cut that still delivers ~80% of the value), and `cost_estimate` (a string, not a number, so it degrades gracefully). `counter_case` is a **required** field (no default) on `alan.dispatch_proposal.DispatchProposal` — the ONE proposal model both human dispatch doors (build-chat and explore-chat) validate a `status: ready` reply against — so a proposal missing it fails Pydantic validation inside `alan.routes._chat_router.parse_dispatch_proposal_yaml` and both doors 422 identically (`dispatch_proposal_parse_failed`); there is no door-specific error branch left to diverge.

Every door's `EXTRACT_DISPATCH_YAML` contract, composed via the shared `_counter_case_block(indent)` helper in `alan/claude_cli.py`, instructs the model to always populate `against` and `cheapest_80` with real content, and to write `cost_estimate` by citing the measured shop-stats block (P5.1's `assemble_shop_stats_block`) when the `## Measured shop stats` section is present in the prompt, or the honest literal `"insufficient data"` when it is absent or stale — never fabricating a number. This is advisory only: the counter-case is always produced and rendered, and nothing in this codebase blocks, delays, or auto-declines a dispatch on its content.

The human's decision to proceed despite the counter-case (the "waiver") is logged exactly once, at the single backend site that actually commits a dispatch: `alan.routes.workspaces.dispatch_task_team` (`POST /api/workspaces/{id}/tasks/{id}/dispatch`), after `enqueue_with_pending_workflow` succeeds — a failed enqueue writes no audit line. Build-chat and explore-chat's atomic create-and-dispatch flows both funnel through this same endpoint, so gating the log write on `DispatchBody.counter_case` being present (vs. `None` for a manual/scripted dispatch that never showed one) is sufficient without duplicating the write site. The write uses the same `append_jsonl_audit` pattern as `predispatch_findings.jsonl` (`alan/teams/_audit.py`), landing one JSON line — timestamp, the dispatched subtask's `task_id` and `title`, the `counter_case` shown, `human_proceeded: true` — in `counter_case_waiver_audit.jsonl` under `alan.roots.logs_root()`, which honors the `ALAN_LOGS_ROOT` override (clause 7): tests and dev sessions that set `ALAN_LOGS_ROOT` never write into the live `~/.alan/logs/`.

**P6.2 — one gated dispatch door.** Before this PR, build-chat's `/extract` and ws-chat's `/propose` were two independently-implemented proposal-generation paths that happened to converge only at the final dispatch-audit site (`dispatch_task_team`'s counter-case-waiver log). Now `alan.routes._chat_router.run_dispatch_proposal` is the single implementation both doors call — it sends the shared `DISPATCH_PROPOSAL_SENTINEL`, parses via `parse_dispatch_proposal_yaml`, and merges a server-side `scan_predispatch` scan into `scope_audit` before returning. `tests/test_dispatch_gate_invariant.py` is the proof-test: it asserts every registered human dispatch door's source calls `run_dispatch_proposal`, and documents (with rationale) why the raw `dispatch_task_team`/`create_workspace` endpoints are intentionally NOT gated here. The gate is advisory everywhere and, critically, **headless-safe**: the fully-autonomous roadmap-driver and primary instance dispatch through the same `create-workspace(title, acceptance_clauses, ...) → dispatch` contract with no human to click through the modal — the counter_case is still produced and (when supplied) still audited via `maybe_log_counter_case_waiver`, but nothing in the propose→dispatch path blocks waiting for a human response.

**Fast-follow — explore-chat joins as the third gated door.** Explore-chat's Dispatch button originally bypassed this gate entirely (raw create-workspace-then-dispatch, no proposal step), which was drift against the P6.2 DoD rather than an intentional exemption. `POST /api/explore-chat/sessions/{sid}/propose` (see `explore_chat.md`'s "Commitment gate as an action" section) now funnels through this SAME `run_dispatch_proposal` implementation — at the time, a third entry in `HUMAN_DISPATCH_DOORS` alongside build-chat and the workspace-discussion advisor; the advisor door's later removal has since left the registry at two entries (`tests/test_dispatch_gate_invariant.py::test_only_two_human_dispatch_doors_are_registered`). Explore's door needed one generalization this PR made to the shared model rather than duplicating it: `alan.dispatch_proposal.DispatchProposal`'s new-workspace title/team constraint (`title is not None ⟹ team == NEW_WORKSPACE_TEAM`) was build-door-specific — Explore mints a titled (new-workspace) proposal for a *consultant* team, not `implementation_plan`. The validator now resolves its allowed-team set from an optional Pydantic validation-context key, `dispatch_proposal_mod.ALLOWED_NEW_WORKSPACE_TEAMS_CONTEXT_KEY`, read via `ValidationInfo.context` inside the `mode="after"` validator; `context=None` (i.e. every call site that does not pass one — this build door included) still defaults to `{NEW_WORKSPACE_TEAM}` byte-for-byte, so build-chat's own `model_validate` calls are unaffected by the new mechanism. The kwarg threads `run_dispatch_proposal(allowed_new_workspace_teams=...)` → `parse_dispatch_proposal_yaml(...)` → `_build_dispatch_proposal_ready(...)` → `model_validate(proposal_obj, context={...})`; only `propose_explore_dispatch` ever passes a non-`None` value, and it passes the session's own consultant team as a singleton set, so a wrong team still 422s rather than being silently accepted or silently pinned.

**Fast-follow (explicitly out of scope here):** the PM ritual's daily digest is autonomous/proactive and has no human-at-keyboard moment to show a counter-case and capture a one-click waiver against. Wiring a counter-case into that surface needs its own adaptation — emitting the counter-case into the digest record at proposal time and capturing the waiver at whatever later action commits the dispatch — and is deliberately deferred rather than silently dropped.

## Propose-time collision fold, server-side and session-attributed

Before this fold, `DispatchProposalModal` ran its own client-side collision check (`useCollisionCheck(description)` with no `chatFamily`/`sessionId`) the instant it opened — on this door, duplicating the check the Summary tab had already run on the same brief seconds earlier, and landing unattributed in the global collision stream instead of this session's `collision_run_summary`. The check is now folded into the SAME gated `run_dispatch_proposal` path documented in `chat_shared_mechanics.md`'s "Propose-time collision fold" section (read that section for the full mechanics — the peer `asyncio.create_task` alongside `scan_task`, the fail-open `_safe_collision_check`/`SAFE_RESULT` wrapper, the `_cancel_with_grace` cleanup, and the `DispatchProposalReady.collision: CollisionVerdictOut` field with its headless-safe default). This door's specifics:

- `_build_dispatch_collision(session_id, root, workspaces_root)` (`alan/routes/build_chat.py`, sibling to the existing `_build_dispatch_scan`) is the `collision` closure `propose_build_dispatch` passes to `run_dispatch_proposal`: it loads the saved brief via `build_chat_mod.load_brief` (falling back to `""` if none exists yet — mirrors `_build_dispatch_scan`'s own fallback), resolves this session's `collision_stream_path` via `alan._chat_core.collision_stream_path(build_chat_mod.CONFIG, session_id, root=root)`, and calls `alan.collision.check_collision(description, workspaces_root=..., stream_path=...)` — **no** `exclude_task_id`, since no workspace exists yet at build-chat propose time to exclude (same rationale `_build_dispatch_scan` already documents for its own `exclude_task_id=None`).
- The run's usage lands in this session's `collision_stream.jsonl` (next to `session.json`/`stream.jsonl`/`brief.json`), and the existing `compute_collision_run_summary`/`ChatSessionResponse.collision_run_summary` plumbing (already wired for this door before this change — see `alan/routes/_chat_router.py`) surfaces it on the session `GET` exactly as before; this fold is what actually makes that field non-null in practice for the first time, since nothing previously ran a collision check against this session's `collision_stream_path`.
- **Re-run keeps using the existing global `/api/collision-check` endpoint** (`chat_family: "build"`, `session_id`) — unlike the workspace door (which needed a new task-scoped route because the shared endpoint has no `task_id`), build-chat's brief-editing flow already had a session id to pass, so no new endpoint was needed here. This re-run affordance now lives only on the Summary tab's own pre-existing `CollisionBox` (see "Frontend" below) — the collapse-chat-dispatch-modal-into-summary-tab work dropped the propose-time collision box's own, duplicate re-run control along with the rest of the modal for this door.
- **The propose-time collision fold itself is unchanged and still runs** — `run_dispatch_proposal`'s peer collision check still executes on every `/propose` call and its usage still lands in this session's `collision_stream.jsonl` (see `read_collision_usage`/`collision_run_summary` below) — but the `DispatchProposalResponse.collision` verdict it returns is no longer rendered anywhere in the Build door's UI (the inline `ProposalPanel` deliberately drops it as a duplicate of the Summary tab's own check, see "Frontend"). The propose-time check still contributes to spend tracking; it simply has no dedicated display or re-run control of its own anymore for this door.
- **The Summary tab's own `useCollisionCheck` call is unaffected and remains a live caller** (`auto: false`, `chatFamily: "build"`, `sessionId`, triggered right after summarize) — it is a different, earlier check against the just-summarized brief, not the propose-time one; both independently write to the same session-scoped `collision_stream.jsonl`, and `read_collision_usage` sums across whatever runs land there, so the panel's collision-spend row reflects both.

## Brief persistence

Summaries are stored as `brief.json` sidecars next to `session.json` (`BuildChatBrief`). `/propose` never calls `save_brief` — the user-edited summary is written only by `/summarize` and the brief PUT, so proposing never clobbers the edited brief (D09's edit-then-dispatch flow).

## Repository binding (`engine_key`)

Every build-chat session is bound to exactly one repository at creation time and never re-pointed afterward. `ChatSession.engine_key: str | None` (`alan/_chat_core.py`) is the shared, optional-typed field every chat family carries; `CreateBuildChatBody.engine_key: str = Field(min_length=1, max_length=200)` is the route-level requirement that actually enforces the binding — a create POST with no `engine_key` key in the body 422s before anything reaches disk, so a session's binding is always a concrete engine slug from the moment it exists (the field stays `str | None` on the model purely so legacy on-disk records without the key still validate, see "Legacy backfill" below). No mutation route (`/messages`, `/interrupt`, `/summarize`, `PUT /brief`) accepts `engine_key` — immutability by omission, the same pattern `project_id` and `cli_session_id` already follow. `GET /sessions/{id}` returns `engine_key` on `BuildChatSessionResponse` straight from `session.engine_key` (previously it derived from `project_mod.engine_key_for(session.project_id)`, so a project-less session always read `null`; that derivation hop is gone), and both `GET /sessions` and `GET /sessions/{id}` now expose it as `BuildChatSessionSummaryOut.engine_key`/`BuildChatSessionResponse.engine_key` so listings don't need a follow-up fetch per row. `project_id` stays optional and orthogonal — a session may have no project, and a project's own `engine_key` is never consulted for this session's binding.

`create_build_chat_session` calls the shared `alan.routes._chat_router.validate_create_binding(engine_key, project_id)` before anything reaches disk: it must resolve via `engine_config.lookup_by_slug` (a registered engine) or equal `engine_config.default_engine_config().repo.slug` (alan's own repo, always valid without registration, since it is the repo alan already runs from) — anything else 400s. When the body also carries `project_id`, and that project already has its own bound `engine_key` (`project_mod.engine_key_for`), the two must match or the create 400s — a project may not acquire a session bound to a different repository than the one it's already bound to. A dangling `project_id` or a project with no `engine_key` of its own skips this check (nothing to conflict with). `alan/routes/explore_chat.py::create_explore_chat_session` calls the SAME shared validator (see `explore_chat.md`) — there is one binding-validation implementation, not a per-door copy.

`_build_dispatch_scan`'s `scope_engine_key` (fed into `scan_predispatch` at `/propose` time) is `session.engine_key` directly — previously it derived from `project_mod.engine_key_for(project_id)` and was `None` whenever the session had no project. A project-less build-chat session now scopes its predispatch duplicate-work scan to its own bound repo instead of degrading to the alan default.

### Legacy backfill

Sessions written before this field existed lack the `engine_key` key in their `session.json` entirely. Two independent mechanisms converge them on alan's own repo (`engine_config.default_engine_config().repo.slug`):

- **Read-time bridge** (`_bridge_legacy_engine_key` in `alan/_chat_core.py`, modeled on the existing `_bridge_legacy_cli_session_id`): `load_session` checks `"engine_key" not in raw_obj` and, if so, rewrites the session with the alan-own-repo slug before returning it. One-shot — the key is present (even if the *value* happens to equal the alan slug) on every subsequent load, so it never re-fires.
- **Boot-time sweep** (`sweep_legacy_engine_keys`, exported from both `alan/build_chat.py` and `alan/explore_chat.py`): called from `alan/routes/infra.py::_run_build_chat_reconciler`/`_run_explore_chat_reconciler`, right next to `reconcile_in_flight_turns` inside `lifespan`. It scans the session directory once for entries whose `session.json` lacks the `engine_key` key, then drives `load_session` (which read-time-bridges, see above) on exactly those legacy session IDs — not the full `_iter_valid_sessions` listing, so a directory with more legacy sessions than the 25-row list cap still gets every one of them backfilled at boot, and already-current sessions aren't redundantly reloaded. Read-time bridge alone would only guarantee "no session that is ever read lacks a repository"; the boot sweep is what makes the guarantee unconditional. The sweep runs *before* `reconcile_in_flight_turns` in both reconciler functions specifically so its own "backfilled N session(s)" log line is observable — `reconcile_in_flight_turns` also loads every session and would otherwise silently absorb the bridge itself.

## Repository provisioning

Before this work, build-chat's `ChatRouterCtx` left `pre_turn`/`resolve_cwd` unset, so `alan.routes._chat_router.do_turn` always passed `cwd=None` regardless of the session's own `engine_key` binding — a build chat bound to a non-alan repository still ran its turns against alan's own checkout. `alan/routes/build_chat.py` now wires `pre_turn=_build_pre_turn, resolve_cwd=_build_resolve_cwd` into `_CTX`, copied in shape from explore-chat's own `_explore_pre_turn`/`_explore_resolve_cwd` (see "Chatting against the bound session's own repo" in `explore_chat.md` for the shared mechanics — the `alan.explore_chat_repo.needs_repo`/`provision` primitives, the clone command, and the credential path are identical for both doors).

`BuildChatSession.repo_provision` (`alan.explore_chat_repo.RepoProvisionStatus`, now shared with explore-chat rather than duplicated) tracks `UNCHECKED → PENDING → READY | NOT_NEEDED | ERROR`. `READY` and `NOT_NEEDED` are frozen once reached — since turns resume the underlying `claude` conversation via `--resume` rather than replaying it, a mid-conversation repo refresh would hand the model contradictory views of the same paths across turns, so the checkout (or the decision that none is needed) is fixed for the session's whole life. `ERROR` is retried on the next turn. Provisioning runs lazily inside the background thread of the first turn that needs it (message send, summarize, or propose), never eagerly at create/bind time.

`_build_resolve_cwd` returns `build_chat_mod.repo_dir(...)` only when `repo_provision == READY`, and `None` for every other status. This is load-bearing: for a bound non-alan session, `resolve_cwd` returning `None` is indistinguishable from "no binding" and means the turn silently reads alan's own codebase instead — exactly the defect this work closes. A `READY`-but-missing checkout (e.g. deleted out from under the session) must re-provision or raise, and must never fall back to `None`; today that means the reaper below always pairs its `rmtree` with an `UNCHECKED` reset in the same step, so a reaped session's next turn re-provisions from scratch rather than reaching `resolve_cwd` in a `READY`-but-empty state.

The checkout lives at `alan.build_chat.repo_dir(session_id, root=...)` — `session_dir(sid)/repo` — computed only from the FastAPI-injected `BuildChatSessionsRootDep`, so it inherits `ALAN_BUILD_CHAT_SESSIONS_ROOT` isolation and `delete_session`'s existing `rmtree` cleanup for free; no new `ALAN_*` variable was needed.

**Boot-time reaper.** `alan.build_chat.reap_stale_repo_checkouts(root=..., now=...)` runs from `alan/routes/infra.py::_run_build_chat_reconciler`, right after the existing `reconcile_in_flight_turns` call, on the same boot-only cadence (every merge to `main` restarts the service, so there is no need for an in-process scheduler). It walks `list_sessions` (capped at 25, the same list-cap every other chat-family sweep accepts), loads each session, and reaps one whose `repo_provision` is `READY` or `ERROR` and whose last activity — the latest transcript message's `ts`, falling back to `created_at` when the transcript is empty — is more than 24 hours old (`_REPO_REAP_TTL_S`, a fixed literal, not user-facing `ALAN_*` config). Reaping `shutil.rmtree`s the checkout and resets `repo_provision` back to `UNCHECKED` **in the same step** — never leaving a session in a `READY` state whose directory no longer exists, which is exactly the unsafe state `_build_resolve_cwd` must not silently paper over. `UNCHECKED`, `PENDING`, and `NOT_NEEDED` sessions are left untouched regardless of age. This reaper is build-chat-only; explore-chat's identical exposure (a checkout that lives for the life of its session with no sweep) is a known, deliberately unaddressed gap — explore-chat conversations are typically much longer-lived and more actively supervised than a build brief, so the risk profile differs, but closing it is left as a follow-up rather than folded into this change.

**Two prompt corrections.** `format_build_system_prompt` no longer states that the assistant may read `~/.alan/workspaces/` for context — that directory sits outside the reachable boundary for every chat surface, and the sentence was always false. It also now composes `alan.claude_cli_grants.BUILD_REPO_BINDING`, a `{repo_label}` template naming the repository the conversation is bound to, resolved via `alan.explore_chat_repo.repo_label(session.engine_key)`: the bound repo's own slug when `engine_key` resolves through `engine_config.lookup_by_slug`, else the literal `"alan (this repository)"` (`alan.claude_cli_grants.OWN_REPO_LABEL`) — the fallback for an unregistered or absent `engine_key`, not a special case for alan's own binding, since alan's own repo is itself registered via `config/engines.d/alan.yaml` in production. The label is threaded through both `_CTX.system_prompt` and `_prompt_with_shop_stats`' inner closure — both receive the `session`, so `dataclasses.replace` in `_ctx_with_shop_stats` can never drop it. `_EXPLORE_PROMPT_INTRO` carries the byte-identical false workspaces claim and is deliberately left alone here — explore-chat is out of scope for this change; see its own architecture doc.

**Credentials and errors.** A private non-alan repository's transport credential comes from the existing `alan.secrets_store.transport_env`/`resolve_secret` mechanism — nothing new was added here. A missing credential surfaces as an ordinary `alan.explore_chat_repo.RepoProvisionError` (wrapping `secrets_store.MissingSecretError`), which `_build_pre_turn` turns into a `ClaudeCliError`: an SSE `error` event on `/messages` and a `502` on `/summarize` or `/propose`, exactly like any other provisioning failure — never an uncaught `500`, and the credential's value is never included in the error message, the transcript, or the brief.

**Accepted risk, unchanged from explore-chat.** A cloned non-alan repository's own `CLAUDE.md`/`.claude/` files are auto-loaded by the `claude` CLI into the turn's `cwd` exactly as they would be for any other checkout — this is a pre-existing trust boundary shared with explore-chat (see `explore_chat.md`), not something this work introduces or widens.

## Dispatch (frontend)

Dispatch is a single atomic client-side call, `useDispatchWorkspace.dispatchWorkspace` → `api.createAndDispatchWorkspace(title, description, "implementation_plan", { instructions, counter_case }, { acceptanceClauses, projectId, roadmapItemId, engineKey })` — one `POST /api/workspaces` with `team` set, no separate `dispatchTeam` follow-up call. `engineKey` is `chat.engineKey`, the session's own repository binding (see "Repository binding" above); `useDispatchProposalFlow`'s `DispatchWorkspaceFn` carries it from the confirmed proposal's flow-level `engineKey` option through to this call. This is what lets a project-less, non-default-repo build-chat session dispatch its workspace against its own bound repo — without it, `alan/app/workspace_creation.py::resolve_engine_key` only derives an engine from `project_id` and silently falls back to alan's own repo for a project-less session.

`/propose` returns either `status: ready` (`proposal.title` + `proposal.acceptance_clauses`; description = edited brief; plus the `collision` verdict, see above) or `status: need_more_info` (render the Open-Questions tab keyed by array index — the shared `DispatchProposalNeedsInfo.questions` is a flat `list[str]`, not `{id, question}` objects; the user answers, the answers are composed client-side into a `## Clarifications` block appended to the brief, then the brief is re-proposed).

## Frontend

`/build` route → `BuildChat.tsx` (two tabs: Chat / Summary). It composes the shared `ChatScaffold`/`ChatPanel`/`ChatSummaryTab` components and the `useUrlDraftSession`/`useChatComposerActions` hooks (`ChatPanel` renders the shared `ChatComposer` input, and the Summary tab embeds the shared `EditableBrief` editor — both reused across chat surfaces); `useBuildChatSession` is a thin wrapper over `useChatSessionGeneric` that separately fetches the session's own `project_id`/`engine_key` (`useSessionBinding`, since the generic hook's `ChatSessionShape` carries neither), clearing both to `null` at the start of every sessionId change and on a failed fetch rather than leaking the previous session's binding, and threads both into `createNew` (`api.createBuildChatSession(engineKey, projectId)`) so "clear and start over" rebinds the replacement session to the same repository/project instead of the client-side default (mirrors `useExploreChatSession.ts`'s `engine_key`-only version, see `explore_chat.md`'s "Frontend" section).

**The Summary tab renders the dispatch proposal inline — no dialog, no separate Open-Questions tab.** The collapse-chat-dispatch-modal-into-summary-tab work collapsed the former three-step flow (Chat → Summary → confirm in a `DispatchProposalModal`) to two steps: `ChatSummaryTab` takes a `renderProposal: (liveBrief: string) => ReactNode` render prop instead of the old `onAction`/`busy`/`actionLabel`/`busyLabel`/`testId`/`error` props, and renders `{renderProposal(liveBrief)}` right after its existing `CollisionBox`. `DispatchProposalModal` itself is now deleted — its last two callers, the Workspace Discussion advisor (`WorkspaceChatPanel.tsx`) and the Inbox answer-in-place door, are both gone.

**`useDispatchProposalFlow.ts` is the shared propose→panel→dispatch hook** both `BuildChat.tsx` and `ExploreChat.tsx` consume (extracted when Explore joined as the third gated door — see `explore_chat.md`'s "Frontend" section). Its whole propose lifecycle — idle, proposing, a propose failure, open questions with their typed answers and their own submit sub-state, a ready proposal, and the flow's own dispatch-failure message — is one `ProposalFlowState` value, produced by `proposalFlowReducer.ts`'s handler-table `proposalFlowReducer` (a standalone module importing neither the hook nor the panel, mirroring the `chatSessionReducer.ts` shape from the chat-session-state work). `proposalFlowReducer.ts` also owns `PendingReadyProposal`, the `flowErrorOf`/`clarificationsOf` selectors, and the `PROPOSAL_FLOW_IDLE` initial value. `propose_resolved`/`propose_failed` are accepted from every state kind with no request-id guard — the brief's only overlapping-request guarantee is that the last propose result wins; `propose_started` while questions are open marks their `submit` sub-state `submitting` instead of leaving the questions view, which is how a re-propose or a `submitAnswers` call in flight (or failed) keeps the open-questions view on screen rather than flipping to a bare pending/error display. The hook owns `resolveImmediate`/`resolvePending` (a caller feeds it either an already-resolved response or a promise — both doors' prefetch, described below, uses both, dispatching `propose_started`/`propose_resolved`/`propose_failed` as appropriate); `submitAnswers` (composes `## Clarifications` via `composeClarifications` from `clarificationsOf(state)`, PUTs the brief, re-proposes — tagging the resulting `ready` state with the *original*, pre-clarifications brief as its staleness key, since the visible Summary-tab brief never changed, only the answers did, while still carrying the composed text forward as the `dispatchDescription` actually sent on dispatch); and `renderProposal: (liveBrief: string) => ReactElement`, built with `createElement(ProposalPanel, {...})` (the hook is a `.ts` file, not `.tsx`) closing over the hook's own `state` plus a per-door `ProposalPanelDoorConfig` (idle/pending testid+label, and the `QuestionsTab` testid+labels) passed in via the hook's options — this one render-prop call is what keeps the two doors' propose/dispatch wiring from being flagged as jscpd duplication. Dispatch-in-flight stays independent of `state`, tracked by the hook's own `useAction()` (the same mechanism the page's own dispatch flag uses) rather than folded into the reducer; the page's `workspaceDispatching`/`workspaceDispatchError` (from its own `useDispatchWorkspace`) are forwarded into `ProposalPanel` untouched as `pageDispatching`/`pageDispatchError` and combined only at render time — `busy = dispatching || pageDispatching`, and the trailing error banner is `flowErrorOf(state) ?? pageDispatchError` — rather than merged inside the hook the way the retired `combineDispatchUiState` used to.

`ProposalPanel` (`features/chat/components/ProposalPanel.tsx`) switches on the flow's own `state.kind` — `idle | proposing | propose_failed | questions | ready | dispatch_failed` — rather than deriving a separate view-state: `idle`/`proposing`/`propose_failed`/`dispatch_failed` share one button (the door's own testid, e.g. `build-plan`/`dispatch-explore`), busy while `state.kind === "proposing"` or the combined `busy` flag is true; `questions` renders the shared `QuestionsTab` component (`features/chat/components/QuestionsTab.tsx`, parameterized by `actionLabel`/`busyLabel`/`testId` so each door keeps its own copy and test id — `dispatch-build` for Build, `dispatch-explore-questions` for Explore), which owns its own action button and inline error (`flowErrorOf(state) ?? pageDispatchError`), so the panel renders no separate primary button alongside it; `ready` renders `DispatchProposalFields` (`features/chat/components/DispatchProposalFields.tsx` — the title/engine/roadmap-item/rationale/acceptance-clauses/counter-case block, originally extracted so `DispatchProposalModal` and `ProposalPanel` could share one implementation; `DispatchProposalModal` is now deleted, so `ProposalPanel` is its sole consumer) plus a `dispatch-proposal-confirm` button whose `onClick` calls `onConfirm(state.ready, instructions)` — there is no separate "stale" state kind; staleness is one inline render-time comparison, `state.kind === "ready" && state.ready.briefContent !== liveBrief`, computed once per render, since the flow never receives brief edits and so can't track staleness itself. A stale ready proposal renders the same fields dimmed (container chrome and the button both take the existing `opacity-70` control idiom, proposal prose stays full-contrast) behind a `dispatch-proposal-repropose` button instead, so confirming can never silently commit a proposal generated against different text than what the person is looking at. `dispatch_failed` renders exactly like `idle` (same shared button) plus the trailing error banner — a commit failure clears the ready proposal synchronously (`commit_started` resets `ready`/`dispatch_failed` back to `idle` before the dispatch call even starts, and a rejection lands unconditionally on `dispatch_failed` from whatever kind was current), so the failure has to surface as a banner alongside the idle-shaped button rather than annotating a state that's already gone; at most one error banner is ever visible, since a `questions` or `propose_failed` kind already renders its own and the trailing banner is suppressed for those two kinds. A single persistent `<output data-testid="proposal-panel-status">` (the `WorkspaceChatPanel.tsx`-precedented live-region idiom) sits outside this state switch and only has its text rewritten per state, so screen readers get the panel's own announcement in place of the dialog's removed focus-trap-and-announce behavior — see `docs/DESIGN_SYSTEM.md`'s modal-key-convention section for why this panel deliberately does *not* wire `handleModalKeyDown`/Ctrl+Enter. The propose-time collision verdict on `DispatchProposalResponse.collision` is not rendered here (see the "Propose-time collision fold" section above); the description `MarkdownPanel` the old modal showed is also dropped as redundant with the brief already visible above the panel.

Session id persists via the `?s=<session_id>` URL param (managed by `useUrlDraftSession`, which auto-creates a draft session and back-fills the param while preserving any other existing query params verbatim). The "Start Build" button lives on the workspace list. A prior change removed the `?description=` deep-link seam that used to let `DeliverySummaryPanel`'s deferred follow-ups pre-fill a new Build draft — that carry-forward now happens through project promote-to-doc (`docs/architecture/project_doc.md`), not a URL param (see `docs/architecture/referral.md`'s tombstone for the related `ChatOrigin`/referral removal).

**Both Build and Explore prefetch, and both now auto-materialize the result with no click.** `useProposePrefetch(sessionId, refreshRunSummary, deps)` fires the injected `deps.propose(sessionId)` right after summarize resolves (2026-07-21 dispatch-flow speed audit F7; Explore joined at prefetch parity in a follow-up PR) — `deps: { propose, interrupt }` is injected per call site (`BuildChat.tsx` passes `{ propose: api.proposeBuildDispatch, interrupt: api.interruptBuildChatSession }`, `ExploreChat.tsx` the explore-chat equivalents) rather than the hook hard-coding a build-chat-only endpoint, which is what let Explore adopt the same hook unmodified. Each page's own `triggerPropose` helper (called from the `onSummarized` callback, right alongside `prefetch.issue`) immediately calls `prefetch.consume(sessionId, content)` and routes the outcome to `flow.resolveImmediate` (settled) or `flow.resolvePending` (still in flight) — in the same tick, with no button click required — so the Summary tab's inline panel usually shows a settled (or at least visibly pending) proposal the instant the person arrives. The panel's own primary button, when clicked in the `idle`/`error`/`stale` states, falls back to the hook's plain `requestPropose(liveBrief)` (a direct, non-prefetch-aware propose call) rather than threading prefetch through the render prop — acceptable because by the time any of those states is reachable by a click, either no prefetch was ever issued for this session visit (direct navigation to Summary without going through Summarize) or the session's own prefetch entry has already been consumed and retained (see below), so there is nothing left to gain from routing the retry through `prefetch.consume` too.

`consume`'s lock semantics: a matching entry is marked `consumed: true` rather than being cleared from the ref. The entry stays reachable by `cancelBeforeLockingAction`/`discardStale` — which may still need to cancel that turn's server-side session lock even after its result has been handed off to the dispatch flow — and `entryMatches` requires `!entry.consumed`, so a second `consume()` call against the same (already-spent) brief can never silently replay a stale result; it falls through to the cancel-then-fresh-propose path like any other mismatch.

**One-click "Summarize & Dispatch" composes the existing chain rather than adding a new one.** `alan/web/src/features/chat/hooks/autoDispatch.ts` (pure, no React) defines the four-stage machine — `AutoDispatchStage = "summarizing" | "checking" | "proposing" | "dispatching"` — and `alan/web/src/features/chat/hooks/useAutoDispatchRun.ts` drives it: a single `generationRef` counter, bumped by `start()`/`cancel()`/`stop()`, is the only cancellation mechanism, re-checked (via the `stage()`/`advance()` helpers in `autoDispatch.ts`) after every `await`, so a stale run's later stages resume as pure no-ops rather than clobbering newer state. Both Build and Explore compose the same shared `alan/web/src/features/chat/hooks/useAutoDispatchComposer.ts` (`useAutoDispatchComposer`/`makeOnSummarized`) rather than duplicating the wiring — the two doors' pages differ only in which `useDispatchWorkspace`/`useDispatchProposalFlow` instance they thread through, which is exactly the difference the existing `useProposeTrigger`/`useDispatchProposalFlow` split already isolates.

- **Single-execution guarantee.** For the chat doors, `onSummarized`'s closure (the same one `prefetch.issue` already fires from) returns a `SummarizeFanout { content, collision: Promise<CollisionInfo>, proposal: Promise<DispatchProposalResponse | null> }` — the run's own "checking" and "proposing" stages await those SAME promises rather than issuing a second collision-check or propose call, so one press produces exactly the one summarize, one collision check, and one propose call the manual flow would also have produced.
- **The generation counter's seven bump sources.** Explicit Stop (`stop()`, reason `"cancelled"`), starting a fresh run (`start()`, which itself bumps before running), a manual `handleSend`, a manual `handleSummarize` click (both reason `"cancelled"` — "starting another conversational action... cancels a pending automatic dispatch rather than racing it"), a live per-keystroke brief edit (`ChatSummaryTab`'s new `onLiveBriefChange` prop, wired from `EditableBrief`'s `onChange`) and the blur-triggered brief PUT (`handleBriefEdit`) — both reason `"brief_edited"` — and a session switch or unmount (one shared `sessionId`-keyed `useEffect` cleanup in `useAutoDispatchComposer`, since a dependency-array change fires the previous render's cleanup before the new render's effect runs, and unmount is the same cleanup with no next render).
- **Every stop reason, and why overlap is the only judgement-based one.** `AutoDispatchStop = "overlap" | "summarize_failed" | "propose_failed" | "needs_info" | "brief_edited" | "dispatch_failed" | "cancelled"`. `overlap` fires when the collision verdict the run itself checked is anything other than `"green"` — the *only* stop that reflects a judgement call rather than an inability to proceed, and per the existing collision-check semantics (unchanged by this work) a `"green"` verdict already means "nothing found or nothing checkable," never "verified clear." `summarize_failed`/`propose_failed`/`dispatch_failed` are outright failures of the corresponding network call; `needs_info` is a `status: "need_more_info"` propose response, which cannot proceed without a person answering; `brief_edited` and `cancelled` are the two cancellation-source buckets above. Every stop is rendered by the shared `features/chat/components/AutoDispatchStatus.tsx`/`AutoDispatchStatusRow.tsx` (see `docs/DESIGN_SYSTEM.md`'s "One-click 'Summarize & Dispatch'" entry for the live-region/shortcut rationale) — on a stop, the evidence the run acted on (the collision verdict in `CollisionBox`, the proposal in `ProposalPanel`) is whatever the chain already produced up to that point, still visible in place, so a stop is legible without a second lookup, and the person is left exactly where the manual flow would have left them to continue by hand.
- **Dispatch-failure detection needed a real signal, not a lagging one.** `useDispatchWorkspace.dispatchWorkspace` and `useDispatchProposalFlow.ts`'s `DispatchWorkspaceFn`/`commit` now resolve `Promise<boolean>` (`true` on success, `false` on a caught failure) instead of `Promise<void>` — both catch their own errors internally and never reject, so a caller can no longer infer failure from a rejection, and reading the corresponding `dispatchError` React state back out through a ref immediately after the awaited call is a real race (the state update from inside an async catch block hasn't necessarily flushed by the time the very next line runs). Threading the boolean straight through the return value avoids that race entirely.
- **The counter-case is waived by the press itself.** Committing automatically means the proposal's counter-case is never read before the dispatch it gates proceeds — this is an accepted consequence, not a defect: the counter-case-waiver audit (`counter_case_waiver_audit.jsonl`, see "Devil's-advocate counter-case" above) still records that a human proceeded, because the press of the one-click button *is* the advance authorisation. Nothing about how the counter-case is produced, logged, or displayed changes.

## Per-message operation record (calm-the-chat-reading-experience)

Every persisted `ChatMessage` (`alan/_chat_core.py`) now carries
`operations: list[str]`, a total-with-default field (`default_factory=list`)
so a pre-change `session.json` record with no `operations` key still
validates unchanged, and a message written before this change simply renders
no activity line — there is no backfill. The list is a record of the rendered
tool labels observed during the turn that produced the message, capped at
`_MAX_STORED_OPERATIONS = 200` entries per message
(`alan/routes/_chat_router.py`).

`alan.routes._chat_router._PartialTextTracker` — already the per-turn
accumulator for the assistant's streamed text — gained a sibling
`operations` list and an `observe_operation(event)` method, called from
`do_turn`'s `emit()` right alongside the existing `partial.observe(event)`
call. `observe_operation` delegates to `alan.run_summary.tool_use_event_label`,
which walks an `assistant` stream event's content blocks for the first
`tool_use` block and renders it the same way the run-summary tool-count
chips already render a tool name: `alan.run_summary.tool_use_label(name,
input)` maps a small set of tool names to the input key that best identifies
what the call touched (`Read`/`Write`/`Edit` → `file_path`, `Bash` →
`command`, `Grep`/`Glob` → `pattern`, `WebFetch` → `url`, `WebSearch` →
`query`), rendering `"{name}: {value[:80]}"` when that key resolves to a
non-empty string and the bare tool name otherwise. Both `execute_turn`'s
completed-turn path and `_finish_stopped_turn`'s cancelled-turn path pass
`operations=partial.operations` into the `ChatMessage` they persist, so a
turn stopped mid-flight still keeps whatever operations were observed before
the cancel landed. The turn's own text is never stored as raw tool input — a
`Write` call's file contents, for instance, never reach `session.json`,
only the `file_path` value truncated to 80 characters.

An errored turn (`ClaudeCliError` reaching `execute_turn`'s uncancelled
branch, or an unexpected exception) persists no assistant message at all —
`clear_best_effort` only clears `in_flight_turn` — so there is no operations
record for a turn that never produced a reply.

`alan.run_summary.tool_use_event_label` is a deliberate Python mirror of
`alan/web/src/components/streamSummary.ts`'s `summarizeToolUse` (the
function that already drives the live, in-flight `toolActivity` labels
`useChatSessionGeneric.ts` renders during a running turn) — same tool→key
mapping, same 80-character truncation, same bare-name and `"?"` fallbacks.
The two implementations are pinned equal by a fixture-style parametrized
test (`tests/test_run_summary.py`'s per-mapped-tool cases) rather than by
sharing code across the language boundary, since `jscpd`'s duplication scan
is scoped to `alan/web/src` and cannot see the Python side at all.

All three read paths that surface a session's `messages` —
`GET /api/build-chat/sessions/{id}`, `GET /api/explore-chat/sessions/{id}`,
and `GET /api/workspaces/{task_id}/prep-chat` — return `operations` and
`interrupted` on every message, because all three read what the same shared
`_chat_router` turn pipeline wrote: a partial wiring (some read paths
returning a field, others silently dropping it) would be a write/read
asymmetry, not a smaller feature. There is exactly one response model,
`alan.routes._deps.ChatMessageOut`, and all three routes build it with
`ChatMessageOut.model_validate(message, from_attributes=True)`, so a field the
persisted `alan._chat_core.ChatMessage` gains reaches the wire by being
declared once. The `GET /api/workspaces/{task_id}/chat/sessions/{id}` read
path this section used to name no longer exists (see
[chat_shared_mechanics.md](chat_shared_mechanics.md)), and the duplicate
`alan.routes._chat_router.ChatMessageOut` that split the routes across two
independent models is gone.

`interrupted` is the field whose absence was a live defect: the stopped-turn
path persists `interrupted=True`, the SSE `turn_stopped` handler set it on
local state, but the response omitted it, so the "Stopped" label survived
inside a session and was lost on reload. It is declared `interrupted: bool =
False` — a plain default, not `default_factory` and not `| None` — so the
generated type is required and non-nullable (see "Rule: a defaulted response
field is optional by artefact, not by contract" in
[api_types.md](api_types.md)). Because the model is shared, an archived
preparation-chat transcript now shows the same "Stopped" label for an
interrupted message: an interrupted message is interrupted whichever surface
renders it. `role` is `Literal["user", "assistant"]` on the response, matching
the two-member union the frontend already declared.

On the frontend, `features/chat/components/ChatTranscript.tsx` renders the collapsed
activity line two ways from the one `features/chat/components/ActivityLine.tsx` primitive:
one instance for the in-flight turn (`toolActivity.map(t => t.label)` plus
the `thinking` flag), and one instance attached after each assistant message
whose `operations` array is non-empty, reading `message.operations` — the
persisted record, not the live `toolActivity` state. A conversation that
predates this change shows nothing for its past replies, since there is
nothing to backfill; only a reply produced after both halves of this change
shipped carries a record a reader can expand later.

**Widened disclosure, scoped by variant (calm-the-chat-reading-experience /
unpin-chat-chrome-and-fix-inline-controls).** `features/chat/components/ActivityLine.tsx`
takes an `ActivityLineVariant` (`"flow" | "overlay"`, default `"flow"`)
prop, threaded through `features/chat/components/ChatTranscript.tsx`'s own optional
`activityVariant` prop to both of its `ActivityLine` mount points (the
in-flight `toolActivity` line and the per-message, persisted-`operations`
line). `ChatPanel.tsx` (Build/Explore) mounts `ChatTranscript` with no
override, so it gets the default `"flow"` variant — the in-place,
full-column-width, unbounded expansion this item's brief asked for.
`WorkspacePrepChat.tsx`'s read-only transcript passes `activityVariant="overlay"`
explicitly, which keeps `ExpandedList`'s pre-existing absolutely-positioned,
`max-h-40 overflow-y-auto`, truncating geometry (and the wrapper's
`max-w-[min(80%,65ch)]`) byte-for-byte unchanged — this surface was not
named in this item's scope, so its behaviour does not change. Both
variants share the toggle button, the per-instance `useId`-derived
`aria-controls` wiring, and the collapsed-row sizing; only `ExpandedList`'s
className/li-className and the root wrapper's className branch on
`variant`. An earlier revision of this item shipped the widened, unforked
behaviour onto both out-of-scope surfaces and left the fork-vs-ratify
question open in the PR description without a human answer — this fork is
that question's resolution, not a ratified widening.

## Preparation-chat archival

Dispatching a build-chat session no longer deletes it: `alan/routes/workspaces.py`'s create-and-dispatch path archives the session into the resulting workspace instead — see [prep_chat.md](prep_chat.md) for the archive mechanism, the read-only transcript route, and the workspace cost line it feeds.

## Startup reconcile

`alan/build_chat.reconcile_in_flight_turns()` clears `in_flight_turn` flags left by a prior restart (same pattern as Open Chat), called from `alan/routes/infra.py` lifespan via `_run_build_chat_reconciler`.
